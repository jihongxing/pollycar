本文是供应商调研的统一空白基线。矩阵中的“待调研”不是供应商能力结论，后续必须使用供应商公开文档、受控演示、合同材料、数据处理协议、测试记录或书面答复填充。

本评审现阶段仅批准“平台最终裁决、第三方提供信号”的架构方向；不要求在 UI 原型和合成实现前完成完整供应商调研，不批准真实供应商或生产数据接入。

## 评审范围

本评审覆盖：

- 乘客实名、成年条件、证件采集、活体、人脸比对和核验结果回传。
- 车主身份复用、驾驶资格、车辆材料、保险材料、车辆照片和自动预审。
- 第三方会话、回调、幂等、超时、结果未知、审计、数据留存和删除。
- 第三方能力与 PollyCar 业务规则、人工审核和最终权限之间的边界。

本轮公开资料调研截止于 2026-07-22，优先使用供应商官方产品文档、官方 API 文档和官方安全说明。公开资料只证明产品声称或文档描述的能力，不替代受控沙箱测试、合同审查、数据处理协议和书面商务确认。

本评审不覆盖：

- 具体供应商品牌、商务报价或采购结论。
- 真实身份、真实生物信息、真实车辆材料和生产启用。
- PollyCar 当前车辆准入阈值、配额、安全规则和权限模型的修改。
- 运营后台的完整审核页面设计；仅定义审核所需的能力输入。

## 能力评分口径

供应商调研阶段使用以下评分，不代表最终采购评分：

| 分值 | 含义 | 证据要求 |
| --- | --- | --- |
| 0 | 不提供或明确不支持 | 供应商文档、书面答复或测试记录 |
| 1 | 可通过人工、定制或外围系统补足 | 能力说明和补足成本 |
| 2 | 已有标准能力，但存在地区、终端、数据或流程限制 | 产品文档、演示和限制清单 |
| 3 | 标准能力成熟，边界、失败处理和运营支持清晰 | 文档、演示、测试、SLA 或合同证据 |
| 待调研 | 尚未获得可靠证据 | 必须列出下一步取证动作 |

任何涉及真实数据处理、生产回调、数据删除、合规责任或人工审核责任的能力，不得只凭销售演示记为 3 分。

### 车主材料的阶段性结论

- 本轮没有找到一份公开资料可以证明“身份核验、驾驶资格、行驶证、车辆照片、保险材料、篡改风险和 PollyCar 车辆准入规则”由同一提供方完整覆盖。
- 车主认证应拆为至少两个可替换能力域：身份核验提供方，以及车辆／保险材料识别与人工审核提供方。
- 行驶证 OCR 可以先作为明确的自动化节点；保险责任范围、车辆照片真实性、材料冲突和最终准入仍应保留 PollyCar 规则与人工复核。
- 任何“自动通过”都必须基于 PollyCar 自己的材料完整性、字段一致性、车辆准入和安全规则，不能直接采用供应商总分或总结果。

| G-04 | 加密与密钥 | 传输和存储加密，密钥责任清晰 | 待调研 | 双方按责任边界 | 证据不足不得接入 |
| G-05 | 回调安全 | 签名、时间窗、防重放和来源校验 | 待调研 | PollyCar 接收端必须掌控 | 丢弃异常回调并进入补偿查询 |
| G-06 | 幂等 | 相同请求、回调和重试不会重复创建或授予资格 | 待调研 | PollyCar 必须掌控 | 保持原状态并记录冲突 |
| G-07 | 可用性 | 会话创建、结果查询和回调有明确 SLA 或服务承诺 | 待调研 | 工程与供应商 | 超时转处理中或人工队列 |
| G-08 | 结果未知 | 能处理供应商无法确认的结果，不默认通过 | 待调研 | PollyCar 必须掌控 | 暂不授予权限，支持查询或人工 |
| G-09 | 版本兼容 | SDK、接口、字段和回调变更有通知与兼容策略 | 待调研 | 工程与供应商 | 变更评审和回滚 |

| G-11 | 运营可见性 | 运营可查看任务阶段、缺件、异常和下一步，不查看不必要原始材料 | 待调研 | PollyCar 必须掌控 | 进入人工处理队列 |
| G-12 | 权限隔离 | 供应商、App、运营和审计角色按最小权限访问 | 待调研 | PollyCar 必须掌控 | 拒绝越权访问 |
| G-13 | 事故响应 | 有数据泄露、错误结果、服务中断和供应商事故通知机制 | 待调研 | 安全、隐私和供应商 | 关闭入口、保留人工处理、启动响应 |
| G-14 | 退出与迁移 | 可导出必要业务结果，能替换供应商而不改变用户状态 | 待调研 | PollyCar 必须掌控 | 无退出方案不进入候选短名单 |
| G-15 | 测试环境 | 提供沙箱、合成数据、失败场景和回调模拟 | 待调研 | 工程与供应商 | 无法测试则不得接入 |
| G-16 | 人工服务 | 对异常、争议、误判和紧急事件有支持渠道和时限 | 待调研 | 供应商提供支持，PollyCar 负责用户关系 | 不满足则限制为非关键能力 |

## 不能由供应商单独决定的事项

以下事项必须由 PollyCar 的业务规则、运营授权或最终决策人控制：

- 用户是否完成实名和成年条件。
- 用户是否可以进入乘客功能。
- 用户是否获得车主工作身份。
- 用户是否可以上线、接单或保持接单资格。
- 车辆是否满足车辆准入标准。
- 保险责任是否达到项目要求。
- 是否要求补材料、申诉、复议、暂停、撤销或重新审核。
- 是否允许身份切换、配额使用和安全相关功能。

供应商返回“通过”只能代表其完成了某项检查或产生了正向信号，不能直接触发以上任何权限变化。

## 淘汰门槛

出现以下任一情况，不进入候选短名单：

- 无法明确真实数据的处理地区、留存和删除责任。
- 只能返回“通过／失败”，无法区分处理中、未知、补充或人工复核。
- 无法验证回调签名、重放保护、幂等或结果查询。
- 要求供应商直接控制 PollyCar 账户、身份或车主权限。
- 无法支持沙箱、合成数据和可重复失败场景。
- 无法提供供应商追踪编号、审计信息或事故响应机制。
- 不能在供应商更换时保留 PollyCar 自有的业务状态和用户恢复路径。
- 供应商能力覆盖不足却要求 PollyCar 以人工方式永久补足关键安全能力。

### 当前建议

1. 乘客认证先围绕中国大陆综合实名核身能力做两到三家受控验证，不预先绑定品牌。
2. 车主认证采用“身份核验 + 车辆材料 OCR/质量检查 + PollyCar 规则 + 人工审核”的组合架构。
3. 保险材料暂不承诺全自动判断，先调研字段识别和人工复核能力。
4. 全球平台只在确认中国大陆证件、数据驻留、跨境和业务资质后进入候选短名单。
5. 通用文档 AI 只能作为技术参照，不能因其支持美国或欧洲身份文件就推导其支持中国大陆车主材料。

## 进入 UI 原型前的冻结条件

供应商调研完成前，原型只使用本矩阵定义的能力名称，不使用供应商品牌、SDK 原始页面或供应商状态文案。

进入 UI 原型阶段前必须冻结：

- 乘客认证每个页面状态对应的业务输入和主行动。
- 车主认证每个材料项的自动检查结果和人工复核入口。
- 处理中、未知、失败、补材料、复核中和服务异常的恢复路径。
- 哪些字段展示给用户，哪些字段只进入运营后台或审计。
- 第三方组件进入、退出和返回 PollyCar 的导航协议。
