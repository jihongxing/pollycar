# 多运营主体管理与结算系统评审

## 评审结论

`有条件通过`

通过范围：

- 多运营主体领域模型。
- 运营主体入驻、暂停、迁移、退出和撤销流程。
- 平台 `15%`、运营主体 `45%`、车主 `40%` 资金分配。
- 运营主体清算和车主付款的供应商中立模型。
- 标准付款周期、批次、双人复核、失败恢复和资金案件。
- 平台后台、运营主体工作台和车主 App 的产品结构。
- 不建立资金余额的主体资料、主运营关系和合同快照机器契约准备。

不通过范围：

- 在复式账本与资金对账验收完成前实现运营主体清算、车主付款和提前结算。
- 在多运营主体模块中建立独立余额事实源、累计应付字段或可直接修改的资金状态。
- 真实运营主体商户入驻。
- 真实支付、分账、清算和车主付款。
- 真实提前结算。
- 真实银行账户、商户号、密钥和资金权限。
- 对外承诺真实付款时间。
- 生产启用。

## 核心架构评审

### 分成和责任

评审结论：

```text
平台服务费 = 订单可分配金额 × 15%
运营主体经营份额 = 订单可分配金额 × 45%
车主毛应付款 = 订单可分配金额 × 40%
```

- 普通订单无代垫项目时，车主获得订单总额的 `40%`。
- 支付手续费由平台承担。
- 车主付款手续费由运营主体承担。
- 法定扣缴单独列示，不改变车主 `40%` 毛权益。
- 运营主体收到 `85%` 后，车主 `40%` 仍保持为开放应付款。

结论：通过。

### 主体和车主归属

- 一个运营主体对应一个稳定企业主体标识。
- 同一车主、城市和车辆同时只能有一个有效主运营关系。
- 接单时锁定运营主体和合同快照。
- 迁移不改变历史订单、退款、清算和车主付款责任。

结论：通过。

### 三段资金过程

1. 资金分配单确认 `15%/45%/40%`。
2. 运营主体清算单记录 `85%` 外部清算。
3. 车主付款单关闭车主 `40%` 应付款。

三个过程状态、幂等和对账相互独立，任一外部成功只能来自已验签回调或主动查询。

结论：通过。

## 内部未决事项裁决

### 付款周期

最终结论：

- `T` 是支付、行程责任、资金分配和冻结全部满足条件的账务日。
- 标准车主付款日是下一个可处理结算日 `T+1`。
- 付款日 `12:00` 前生成批次。
- 付款日 `18:00` 前完成复核并提交支付机构。
- 已提交但支付机构仍处理中的，不视为运营主体内部逾期。

理由：

- 不把尚未满足退款、安全和对账条件的订单强行计入付款时限。
- 给运营主体和平台留出日终对账及异常隔离时间。
- 使用可验证的时点判断逾期，避免“尽快付款”等不可执行表述。

结论：通过。

### 逾期和运营限制

最终结论：

- 未在约定付款日提交即触发提醒。
- 逾期超过 `1` 个可处理结算日，停止新增车主、关闭提前结算并降低新订单额度。
- 逾期超过 `2` 个可处理结算日，或确认资金不足、账户冻结，暂停接受新订单。
- 恢复前必须清理逾期、完成对账并由平台财务和运营双人复核。

结论：通过。

### 提前结算

最终结论：

- 保留“提前结算申请”产品能力。
- 不建立车主钱包。
- 车主不能输入任意金额，只能选择 Server 返回的合格应付款。
- 不改变车主 `40%`。
- 车主付款手续费仍由运营主体承担。
- 生产默认 `driver_early_settlement_enabled: false`。

结论：有条件通过；仅允许合成验证。

### 运营主体账户变更

最终结论：

- 强认证。
- 经办和复核分离。
- 默认 `48 小时` 冷静期。
- 新旧企业联系人同时收到通知。
- 支付机构账户一致性验证通过后生效。
- 怀疑账户被盗用时立即冻结，不走普通切换流程。

结论：通过。

### 车主收款账户变更

最终结论：

- 由车主本人在受信设备发起。
- 重新认证和支付供应商验证。
- 默认 `24 小时` 冷静期。
- 冷静期暂停新付款，但不消灭车主应付款。

结论：通过。

### 车主运营主体迁移

最终结论：

- 双方确认、系统校验完成且无进行中行程后，默认下一个自然日 `00:00` 生效。
- 生效前订单归旧运营主体。
- 生效后订单归新运营主体。
- 历史车主应付款、退款和追偿不得迁移。

结论：通过。

### 运营主体退出

最终结论：

- 自愿退出默认提前 `30 个自然日`。
- 严重风险和监管要求可以立即撤销。
- 停止新业务后，依次处理进行中行程、退款、车主应付款、对账差异和资金案件。
- 未清零义务阻止正常进入 `exited`。

结论：通过。

### 风险准备和平台垫付

最终结论：

- 当前不建立平台风险准备金、运营主体保证金或跨主体资金池。
- 平台默认不为运营主体垫付车主应付款。
- 支付机构提供的订单级冻结、分账和退款回退可以作为候选。
- 未来若引入保证金、保险、保函或平台垫付，必须单独决策。

结论：通过为当前设计边界；平台法定保证责任仍是生产门禁。

## 支付机构能力评审

### 微信支付平台收付通

公开能力：

- 支持平台协助二级商户入驻。
- 订单资金进入二级商户账户并可冻结。
- 平台可以收取佣金。
- 公开默认最高分账比例为 `30%`。
- 支持补差、退款、余额查询、提现和账单。
- 官方公开定位为电商行业平台收付解决方案。

评审结论：

- 平台 `15%` 佣金处于公开默认比例范围。
- 运营主体作为二级商户承接 `85%` 是首选候选路径。
- 不能仅凭公开文档认定出行业可以开通，必须取得微信支付针对业务主体和场景的书面准入结论。

状态：生产阻断。

### 支付宝商家分账

公开能力：

- 资金先进入商家支付宝账户。
- 分出金额最高不超过订单金额 `30%`。
- 接收方可以是企业或个人支付宝账户。
- 个人接收方不支持分账回退。
- 商家分账免费。

评审结论：

- 不适合作为直接拆分运营主体 `45%` 和车主 `40%` 的默认方案。
- 不允许首期直接向个人车主分账。
- 需要支付宝提供平台型、多运营主体和车主付款的书面产品方案。

状态：生产阻断。

### 支付手续费

支付宝 APP 支付公开一般行业费率为 `0.6%`，特殊行业为 `1.0%`，实际以签约为准；退款时支付服务费不退回。

评审结论：

- 支付手续费和退款损失继续由平台承担。
- 预算和报价模型必须考虑退款后手续费不返还。
- 不得从运营主体 `45%` 或车主 `40%` 中补扣。

结论：通过。

## 权限评审

通过规则：

- 运营主体付款批次必须经办与复核分离。
- 批准后金额或账户变化使批准失效。
- 平台、运营主体、开发和客服均不能直接修改余额或历史流水。
- 运营主体只能访问本主体数据。
- 平台财务只能执行职责范围内的复核和资金案件操作。
- 冲正只能追加反向分录，不能覆盖原记录。

结论：通过。

## 退款和异常评审

通过规则：

- 车主付款前退款会阻止付款并冲正原分配。
- 车主付款后退款先保障乘车人，再独立追偿。
- 付款未知时只查询原请求。
- 批次部分成功时只关闭成功项。
- 运营主体暂停和退出不影响历史车主查看所得和提出申诉。
- 对账差异非零会阻止清算、付款和关账。

结论：通过。

## 公平性评审

- 所有运营主体使用相同 `15%/45%/40%` 规则。
- 不允许按车主性别、头像、年龄、乘车人偏好或互动结果改变分成、账期和手续费。
- 运营限制依据付款账龄、资金差异、账户和合规状态，不依据受保护属性。
- 公平性指标使用汇总数据，运营主体不得访问无关敏感属性。

结论：通过。

## 剩余生产门禁

### 门禁 1：运输经营和消费者责任

需要法律负责人确认平台、运营主体和车主的运输经营、承运、安全和消费者责任。

### 门禁 2：具体支付产品和行业准入

需要至少一家持牌支付机构书面确认运营主体 `85%`、平台 `15%`、退款回退、车主付款和账单能力。

### 门禁 3：法定会计确认

需要确认运营主体按总额确认 `85%` 还是按净额确认 `45%`。

### 门禁 4：发票和税务

需要确认乘车服务发票、平台服务费发票、车主所得、税率和代扣代缴。

### 门禁 5：运营主体资金不足责任

需要确认运营主体资金不足、破产或拒绝付款时，平台是否依法承担垫付、保证或其他责任。

### 门禁 6：生产资金权限

需要完成生产商户号、收款账户、密钥、权限、轮换、吊销和应急演练。

## 实施准入

允许：

- 编写供应商中立机器契约。
- 实现合成运营主体、车主归属和迁移。
- 实现不包含余额和付款执行的主体资料、合同快照及三端合成页面。
- 为固定 `15%/45%/40%` 分配、清算和付款定义账本交易输入，但不得绕过统一账本过账接口。

资金实现前置门槛：

- 复式账本 PostgreSQL 表、迁移和 Repository 已完成。
- 数据库已经验证拒绝借贷不平衡交易。
- 账本来源事件、交易类型和幂等键唯一约束通过并发测试。
- 历史分录只允许追加和冲正，禁止修改或删除。
- 余额投影可以从全量分录重建为同一结果。
- 资金对账能够覆盖支付、退款、平台 `15%`、运营主体 `85%`、车主 `40%` 和手续费。
- 任意非零对账差异能够阻止清算、车主付款和关账。
- 数据库重启、重复账单、迟到回调和未知结果恢复测试通过。

只有全部前置门槛通过后，才允许：

- 实现固定 `15%/45%/40%` 分配过账。
- 实现合成运营主体清算和车主付款批次。
- 实现双人复核、失败、未知、部分成功和资金案件。
- 验证清算、付款、退款和冲正的跨模块闭环。

条件：

```yaml
production_enabled: false
real_payment: false
real_settlement: false
real_withdrawal: false
driver_early_settlement_enabled: false
real_operator_onboarding: false
```

禁止：

- 真实供应商请求。
- 真实商户和账户资料。
- 真实车主付款。
- 生产结算时间承诺。
- 将合成余额展示为真实可用资金。
- 通过多运营主体 Repository 直接创建、修改或删除余额。

## 验收要求

- 分成唯一口径检查为零差异。
- 一个车主、城市和车辆只有一个有效主运营关系。
- 历史订单不随迁移改变运营主体。
- `T+1`、`12:00`、`18:00` 和逾期规则可由合成时钟验证。
- 账户冷静期和双人复核不能被绕过。
- 重复付款和重复清算被幂等阻止。
- 未知结果不会创建替代资金请求。
- 运营主体退出前所有退款、车主应付款和资金案件清零。
- 所有真实能力门禁保持关闭。
