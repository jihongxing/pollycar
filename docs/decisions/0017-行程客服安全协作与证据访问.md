# 0017 行程、客服、安全协作与证据访问

## 状态

`已批准设计与默认关闭门禁后的合成代码实现；未批准生产启用`

## 背景

运营控制台阶段三需要同时服务平台运营、运营主体人员、客服、安全人员、安全负责人、紧急响应人员和审计人员。行程、安全、资格、通信和资金领域已经拥有各自权威状态，后台不得为了操作便利复制状态、直接修改历史或建立第二套案件结论。

阶段三涉及跨主体信息、聊天与位置证据、限制与恢复访问、应急响应和未知写入结果，属于权限、隐私和安全高风险能力，必须在代码实现前冻结唯一边界。

## 决策

### 1. 功能门禁

- 行程运营使用 `synthetic_admin_trip_operations`。
- 客服、安全、证据访问和恢复任务使用 `synthetic_admin_case_management`。
- 两个门禁均默认关闭，只依赖 `internal_sandbox` 和 `synthetic_admin_multi_organization`。
- 任一门禁开启都不代表真实账号、真实证据、真实外部服务或生产启用获批。

### 2. 唯一事实源

- 行程状态、版本、运营主体快照和恢复结果来自既有行程域。
- 聊天冻结、举报、申诉和安全结论来自既有通信与安全域。
- 资格限制与恢复来自资格域。
- 资金责任与差异只引用资金域，不在阶段三修改。
- 阶段三只拥有运营任务、客服案件、证据访问授权、升级记录和未知结果恢复任务。

### 3. 禁止自由修改行程

后台不提供通用“修改行程状态”能力。所有影响行程的动作必须：

1. 映射到既有领域明确命令；
2. 携带行程资源版本和幂等键；
3. 由服务端重新校验组织范围、角色、行程状态和领域守卫；
4. 返回明确成功、明确失败或未知结果；
5. 未知结果只查询原请求，不得创建替代请求。

### 4. 跨主体可见性

- 行程归属使用行程创建或接单时固化的运营主体快照，后续主运营关系迁移不改写历史行程。
- 运营主体人员只能查看本主体关联行程和分配给本主体的协作任务。
- 跨主体案件由平台创建单一案件，并向各主体投递隔离的协作任务。
- 任一运营主体不能查看另一主体的内部备注、人员身份、用户联系方式、聊天原文、完整位置轨迹或安全结论依据。
- 安全案件向运营主体仅披露必要的协作动作、截止时间和完成状态。

### 5. 客服与安全隔离

- 客服可查看行程摘要、用户可见沟通记录和客服案件时间线。
- 客服不得查看安全证据原文、完整轨迹、举报方身份或安全调查备注。
- 客服可升级安全案件，但升级后只能查看安全域返回的最小状态和业务动作。
- 安全人员不得直接修改客服责任、资金结论或行程历史。

### 6. 安全恢复职责分离

- 安全冻结经办人不得独立批准恢复。
- 恢复访问必须由不同的安全负责人独立复核。
- 严重事件恢复还必须确认应急响应、证据保全、资格同步和未关闭风险均已完成。
- 安全案件关闭不会自动改变客服、审核、资金或运营主体结论。

### 7. 证据访问

- 默认只展示结构化摘要和遮蔽字段。
- 原文访问必须关联案件、工单、明确目的、字段清单、最长有效期和审计。
- 普通限时访问最长三十分钟；紧急破窗访问最长十五分钟。
- 聊天原文、完整位置轨迹和导出均要求双人批准。
- 访问到期、角色切换、案件切换或组织上下文变化后立即重新遮蔽。
- 阶段三合成实现不接收真实聊天、真实轨迹、真实身份材料或真实紧急联系人。

### 8. 未知结果恢复

- 每个写命令记录请求摘要、幂等键、目标资源版本和结果状态。
- `unknown` 必须创建恢复任务并冻结同资源同动作的再次提交。
- 恢复顺序固定为：查询原幂等结果、读取权威状态、核对审计与 Outbox、形成成功或失败结论。
- 技术运维只能判断技术结果，不能替代业务角色作客服、安全或行程决定。

## 后果

- 阶段三页面以任务、案件和权威状态聚合为中心，不形成通用 CRUD。
- 后续代码必须复用阶段一组织上下文、统一授权和追加式审计。
- 已批准在两道默认关闭门禁后进入仅使用合成数据的代码实现。
- 真实数据、真实证据、外部应急服务和生产启用仍需另行批准。
