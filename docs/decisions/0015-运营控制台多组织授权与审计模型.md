# 决策 0015：运营控制台多组织授权与审计模型

## 决策状态

`已批准`

- 批准日期：`2026-07-14`
- 允许范围：机器契约、合成数据、内部沙箱、高保真设计和生产级代码实现
- 禁止范围：真实内部账号、真实运营主体账号、生产权限启用、真实敏感数据披露和生产后台启用
- 功能门禁：`synthetic_admin_multi_organization` 默认关闭

## 背景与待解决问题

既有运营后台使用平面 `staff` 角色支持车辆审核、安全案件和资格轨迹，无法表达平台、运营主体和项目治理组织之间的严格数据边界，也无法可靠约束城市范围、资源范围、临时授权、职责分离和高层只读访问。

阶段一必须在代码实现前冻结唯一授权模型，避免编码阶段在“单角色权限”“组织租户权限”“页面前端筛选”或“临时超级管理员”等候选方案之间临时选择。

## 决策目标与非目标

目标：

- 建立内部用户、组织成员关系、功能角色、作用域和组织上下文的唯一模型。
- 保证运营主体人员不能访问其他主体，平台人员也只能访问显式批准的城市和主体。
- 保证页面导航、深链接、数据查询、字段披露和写操作使用同一授权判定。
- 建立追加式审计事件，覆盖认证、上下文切换、授权判定、数据披露、临时授权和高风险操作。
- 保证高层身份默认只读，不因职级获得日常经办或严格敏感数据权限。

非目标：

- 不批准真实内部身份认证或生产账号开通。
- 不建立通用超级管理员、万能角色或绕过组织范围的支持入口。
- 不替代现有业务领域权限、状态守卫和职责分离规则。
- 不在阶段一实现组织入驻、资金操作或运营主体写操作。

## 可选方案及权衡

### 方案 A：仅使用功能角色

优点：

- 实现简单。

缺点：

- 无法表达同一角色在不同组织、城市和资源上的不同范围。
- 容易把运营主体财务人员错误扩展为跨主体财务人员。

结论：否决。

### 方案 B：每个运营主体建立独立后台应用或独立权限系统

优点：

- 表面上容易隔离。

缺点：

- 产生重复账号、重复权限模型和重复审计链。
- 平台跨主体治理和高层聚合视图难以保持一致。
- 容易形成独立数据和资金事实源。

结论：否决。

### 方案 C：统一内部身份，使用组织成员关系、角色绑定和显式作用域组合授权

优点：

- 同时支持平台、运营主体和项目治理组织。
- 授权判定可以统一应用于导航、深链接、查询、披露和操作。
- 可以表达临时授权和职责分离，且不改变用户真实角色。

缺点：

- 契约和测试复杂度更高。
- 所有查询必须携带并验证组织上下文。

结论：采用。

## 最终决策

### 唯一身份与成员关系

- 一个自然人对应一个 `internal_user_id`。
- 内部用户不能直接持有跨组织权限；权限必须通过 `organization_membership` 生效。
- 一个成员关系只属于一个内部组织，组织类型固定为 `platform`、`operator` 或 `governance`。
- 运营主体成员关系的 `organization_id` 固定，不能通过界面切换为其他运营主体。

### 唯一授权组合

```text
access_decision
= authenticated_internal_user
× active_membership
× functional_role_binding
× organization_context
× city_scope
× operator_scope
× resource_scope
× action
× purpose
× data_classification
× temporary_grant
× separation_of_duties
× feature_gate
```

任何一项不满足时默认拒绝。前端隐藏模块只改善体验，不构成授权边界。

### 组织上下文

- 平台成员可以在已授权平台范围内切换城市和运营主体观察范围。
- 运营主体成员的主体上下文不可切换，只能在本主体获批城市间切换。
- 项目治理成员只能进入聚合只读上下文。
- 上下文切换不增加角色、不扩大最大数据等级，也不自动获得临时授权。
- 所有深链接和 Server 请求必须重新计算授权，不信任客户端保存的上下文。

### 临时授权

- 临时授权只能缩小到一个明确动作、资源或字段披露范围。
- 必须包含工单、业务目的、批准人、开始时间和到期时间。
- 默认最长有效期为 `PT4H`；严格敏感数据披露默认最长有效期为 `PT15M`。
- 临时授权不能绕过职责分离、本人关联限制、功能门禁或生产关闭态。
- 到期、撤销或会话保证等级下降后必须立即失效。

### 职责分离

- 经办人与复核人必须是不同内部用户。
- 高层身份与日常经办身份不得在同一会话目的下合并。
- 技术运维不能执行审核、安全、财务或运营业务决定。
- 审计人员只有只读证据权限。
- 任何本人、关联账户或利益主体冲突必须拒绝。

### 审计模型

- 审计事件为追加式事实，不允许业务角色修改或删除。
- 每次授权判定均生成唯一 `access_decision_id`；允许和拒绝均可审计。
- 数据披露必须记录字段集合、数据等级、目的、工单和到期时间，不记录未遮蔽原文。
- 上下文切换必须记录切换前后范围。
- 高风险操作必须关联授权判定、幂等键、资源版本和结果状态。
- 审计事件必须包含服务端时间、请求关联标识、会话标识和主体用户标识。

### 数据查询约束

- Repository 或查询服务必须接收服务端构造的授权范围，禁止先查询全量数据再由前端过滤。
- 运营主体查询必须带固定 `operator_id` 限制。
- 受控导出与页面查询使用同一授权范围。
- 运营主体名录在阶段一仅提供平台授权角色只读访问，不提供创建、激活或修改入口。

## 产品和业务影响

- 平台工作台可以展示跨主体任务，但只展示当前授权范围。
- 运营主体工作台固定显示主体身份和城市范围，不提供主体切换。
- 高层驾驶舱沿用相同范围模型，不新增高层超级权限。
- 未授权模块不显示；直接访问 URL 时仍返回统一拒绝状态。

## 安全、隐私、合规与公平性影响

- 默认拒绝和服务端范围过滤降低跨主体数据泄露风险。
- 审计事件不保存敏感原文，降低审计系统成为第二敏感数据源的风险。
- 临时授权有目的、工单和时限，可用于受控披露而不是万能提权。
- 真实内部身份、真实组织账号和生产启用仍需独立安全、隐私、法律和离职回收评审。

## 验收标准

1. 运营主体用户访问其他主体列表、详情、深链接和导出均被拒绝。
2. 未授权模块不出现在导航，手工输入 URL 仍被 Server 拒绝。
3. 平台用户切换组织观察范围后角色和最大数据等级不变化。
4. 临时授权到期或撤销后立即失效，且不能绕过职责分离。
5. 登录、上下文切换、允许与拒绝判定、字段披露和高风险操作均生成追加式审计事件。
6. 审计事件不保存严格敏感原文。
7. 三个阶段一高保真页面明确展示组织上下文、范围边界和审计反馈。

## 生效与退出条件

- 本决策立即作为阶段一机器契约和合成实现的唯一输入。
- 真实内部账号和生产启用继续关闭。
- 若未来引入外部身份提供商，只能替换认证机制，不能绕过本决策的组织成员关系、作用域和审计模型。
- 若需要改变组织类型、授权组合或审计不可变性，必须新建替代决策。
