# 决策 0014：平台服务费与多运营主体分成

## 决策状态

`评审中`

- 内部候选结论日期：`2026-07-13`
- 允许范围：服务费与分成规则设计、合成分配计算、复式账本模型和对账模型
- 专项评审结论：`docs/reviews/0008-多运营主体管理与结算系统评审.md` 已有条件通过机器契约准备和合成验证
- 禁止范围：真实收款、真实分账、真实付款、真实提现、真实商户号和生产资金启用
- 实施依赖：复式账本与资金对账先于多运营主体清算和车主付款实现；多运营主体不得建立独立余额事实源
- 关联评审：`docs/reviews/0007-平台服务费与多运营主体分成评审.md`
- 关联设计：`docs/finance/04-服务费与多运营主体分成设计.md`

## 背景与待解决问题

PollyCar 计划由一个平台主体提供产品、撮合、交易秩序、支付协调、风控、账务和技术服务，同时允许一个或多个运营主体负责车主准入、日常运营、服务质量、合同管理和车主结算。

需要把以下口头商业模型收敛为可计算、可记账、可退款和可对账的规则：

- 平台主体获得订单可分配金额的 `15%`。
- 车主运营主体获得订单可分配金额的 `45%`。
- 车主获得订单可分配金额的 `40%`。
- 用户支付产生的支付手续费由平台主体承担。
- 运营主体向车主付款产生的手续费由运营主体承担。
- 一个车主可能在不同时间归属不同运营主体，但一笔历史订单的分成主体和比例不能被事后改变。
- 支付机构普通分账能力存在比例、接收方、退分账和商户模型限制，不能假设一笔交易可以直接按 `15%/45%/40%` 同时完成三方清算。

## 决策目标与非目标

目标：

- 分离平台服务费、运营主体经营份额和车主应付款。
- 建立多运营主体下稳定的车主归属、订单快照和结算责任。
- 保证任何一笔订单的分配金额严格守恒。
- 明确支付手续费、车主付款手续费、退款、优惠、代垫费用和尾差的承担方式。
- 为复式账本、对账、运营报表和未来支付机构选型提供统一事实源。

非目标：

- 不通过本决策批准真实资金生产启用。
- 不最终认定平台、运营主体或车主的运输经营、劳动、税务和发票法律关系。
- 不选择最终支付机构、商户产品、商户号或结算账户。
- 不建立平台储值钱包、运营主体钱包或车主可转让余额。
- 不批准平台或运营主体通过后台任意调整单笔订单分成。

## 可选方案及权衡

### 方案 A：平台收取全部订单款，再直接向运营主体和车主付款

优点：

- 平台对资金路径控制最强。
- 表面上容易实现统一账单。

缺点：

- 平台可能形成集中资金归集、应付款管理和事实资金池。
- 平台需要直接承担车主付款、提现、账户和更重的资金合规责任。
- 与“不建立平台钱包、不自行保管资金”的既有决策冲突。

结论：否决。

### 方案 B：支付机构将一笔订单直接按 `15%/45%/40%` 分给三方

优点：

- 外部资金流与商业比例直观一致。
- 平台不需要再次向运营主体或车主付款。

缺点：

- 微信支付普通商户、服务商分账和支付宝商家分账公开默认最高分账比例均为 `30%`，不能作为 `40%` 或 `45%` 直接分出的默认前提。
- 支付宝商家分账对个人接收方不支持退分账，退款恢复能力不足。
- 三方直接分账会把车主管理、付款失败、退款追偿和运营主体责任拆散。
- 不利于运营主体作为车主合同和付款责任主体承担完整责任。

结论：不作为首期默认方案；只有持牌支付机构书面确认完整支持并通过法律、财务和退款评审后才可重新评估。

### 方案 C：平台收取 `15%`，运营主体承接 `85%`，运营主体确认并支付车主 `40%`

优点：

- 与多运营主体及车主管理责任相匹配。
- 平台 `15%` 处于已核验普通分账公开默认上限内。
- 运营主体承接的 `85%` 中，`45%` 是运营主体经济份额，`40%` 是运营主体对车主的应付款，责任链清晰。
- 可以优先采用平台型收付产品，使订单资金进入运营主体对应的二级商户或受控结算路径。
- 退款、付款失败、运营主体退出和车主追偿可以在明确责任主体下处理。

缺点：

- 运营主体需要具备真实合同、收款、税务、付款、对账和资金安全能力。
- 平台需要维护跨主体的分配子账，但不能把该子账伪装成可提现钱包。
- 运营主体收到 `85%` 后不得把车主 `40%` 误记为自身可自由支配收入。
- 最终会计确认可能因主要责任人或代理人判断而不同。

结论：采用为内部最终候选方案。

## 最终决策

以下规则作为内部最终候选，在本决策获得正式批准前只允许用于设计、合成数据和默认关闭的资金内核。

### 主体和合同链

1. 平台主体提供技术平台、订单撮合、交易秩序、风控、支付协调、账务和运营工具。
2. 每个可接单车主必须在订单接受时绑定一个有效运营主体。
3. 运营主体负责其名下车主的合同、准入协同、服务管理、结算资料、车主付款和付款手续费。
4. 一笔订单只能快照一个运营主体，不允许事后把历史订单迁移给其他运营主体。
5. 该结构不得用于规避网络预约出租汽车平台依法应承担的许可、承运、安全、信息报送或消费者保护责任；平台与运营主体的最终法律角色必须取得专项书面意见。

### 经济分配

订单可分配金额 `allocable_fare_minor` 按以下基点分配：

```text
platform_rate_bps = 1500
operator_rate_bps = 4500
driver_rate_bps = 4000
total_rate_bps = 10000
```

普通订单不存在路桥费、停车费等代垫项目时，`allocable_fare_minor` 等于订单总额，因此车主获得订单总额的 `40%`。存在代垫或依法不得分配的款项时，车主获得可分配车费部分的 `40%`，代垫费用另行按实际承担方全额处理。

计算规则：

```text
platform_share = floor(allocable_fare_minor × 1500 ÷ 10000)
operator_share = floor(allocable_fare_minor × 4500 ÷ 10000)
driver_share = allocable_fare_minor - platform_share - operator_share
```

尾差全部进入车主份额，禁止平台或运营主体通过舍入获得隐藏收益。该尾差规则最多使车主相对理论比例增加两分，不得产生负数或金额不守恒。

### `100 元` 示例

假设订单可分配金额为 `100.00 元`：

| 项目 | 金额 | 资金和责任含义 |
| --- | ---: | --- |
| 平台服务费 | `15.00 元` | 平台经济权益 |
| 运营主体经营份额 | `45.00 元` | 运营主体经济权益 |
| 车主应付款 | `40.00 元` | 运营主体对车主的应付款 |
| 合计 | `100.00 元` | 必须与可分配金额严格一致 |

若用户支付手续费为 `0.60 元`，由平台另行承担：

```text
平台毛服务费 = 15.00 元
平台支付手续费费用 = 0.60 元
平台手续费后贡献 = 14.40 元
```

若运营主体向车主付款手续费为 `0.10 元`，由运营主体另行承担：

```text
运营主体毛经营份额 = 45.00 元
运营主体付款手续费费用 = 0.10 元
运营主体手续费后贡献 = 44.90 元
车主应付款仍为 40.00 元
```

依法需要代扣代缴税费时，车主 `40%` 仍作为税前应得权益，税款必须单独列示为法定扣缴，不得伪装成提现手续费、平台服务费或运营管理费。

### 可分配金额

默认进入 `allocable_fare_minor`：

- 基础车费。
- 距离和时长费用。
- 预约服务费用。
- 已批准的时段或车型价格调整。

默认不进入：

- 路桥费、停车费和其他明确代垫费用。
- 乘车人押金、保证金或预授权冻结金额。
- 平台承担的支付手续费。
- 运营主体承担的车主付款手续费。
- 未经独立决策批准的取消费、违约金、赔偿和安全补偿。
- 税务或监管要求独立归集的款项。

代垫费用按实际承担方全额归还，不参与 `15%/45%/40%` 分配。

### 优惠和补差

- 平台出资优惠不得减少运营主体和车主按原计价基数计算的应得金额；平台通过补差或营销费用承担。
- 运营主体出资优惠从运营主体份额或运营主体营销费用承担，不得减少车主应付款。
- 多方共同出资优惠必须在报价时锁定各出资方和金额。
- 用户实际支付金额、平台补差金额和可分配金额必须分别记录，禁止用一个字段混合表达。

### 订单分成快照

车主接受订单时必须锁定：

```text
platform_entity_id
operator_entity_id
driver_account_id
driver_operator_membership_id
platform_contract_version
operator_contract_version
driver_contract_version
revenue_share_policy_id
revenue_share_rule_version
platform_rate_bps
operator_rate_bps
driver_rate_bps
pricing_rule_version
accepted_at
```

订单接受后，运营主体归属、合同或比例变化只影响未来订单。

### 外部资金路径

- 优先采用支付机构的平台型收付或二级商户模式。
- 候选路径为：用户支付订单款；支付机构按产品能力将平台 `15%` 作为平台佣金或分账，将剩余 `85%` 进入订单运营主体的商户账户或受控结算路径。
- 运营主体收到或被确认享有 `85%` 时，必须同时确认其中 `40%` 为车主应付款；收到 `85%` 不代表运营主体可把全部金额作为自身经济所得。
- 运营主体向车主付款后，车主应付款才可以关闭。
- 车主不从平台钱包提现，平台不得向车主展示可自由转让的平台余额。

### 退款和逆向资金

- 分配前退款：从乘车人待履约资金直接形成退款应付款。
- 已分配但未外部清算：冲正原分配，再形成退款应付款。
- 已清算到运营主体：优先使用支付机构退分账、回退或运营主体可用资金完成原路退款。
- 已向车主付款：先保障乘车人依法应得退款，再依据责任结论和合同向责任方追偿；不得因内部追偿失败无限期拖延合法退款。
- 个人接收方不支持可靠退分账的支付产品，不得用于首期直接向车主分账。
- 退款支付手续费不退或产生额外费用时，默认由平台承担；只有独立决策明确责任方后才可改变。
- 取消费当前保持关闭；未来启用时必须使用独立分配策略，不能默认套用 `15%/45%/40%`。

### 多运营主体治理

- 运营主体必须完成企业身份、合同、收款账户、税务资料、权限负责人和安全联系人验证。
- 一个车主可以保留历史运营主体关系，但同一城市、同一车辆在同一时刻只能有一个用于接单和结算的有效主运营关系。
- 运营主体暂停后不得承接新订单；已接受订单按安全和履约规则完成或退出。
- 运营主体退出不得删除历史订单、分配、付款、退款和对账记录。
- 运营主体余额不足、拒绝退款或无法支付车主时，平台冻结其新订单能力并建立资金案件，但不得直接修改历史账本余额掩盖问题。

### 会计和税务边界

- `15%/45%/40%` 首先是订单经济权益分配，不直接等同于各法定主体财务报表中的净收入。
- 平台是否按净额确认 `15%`、运营主体是否按总额确认 `85%` 并将 `40%` 记为车主服务成本，或按净额确认 `45%`，必须依据主要责任人或代理人判断、合同和正式会计意见决定。
- 候选发票路径为：运营主体向乘车人承担乘车服务开票责任；平台向运营主体就 `15%` 平台服务费开票；车主所得按运营主体与车主的法律关系处理凭证、发票或代扣代缴。
- 正式发票、收入确认、增值税、企业所得税、个人所得税和代扣代缴规则未获书面批准前，不得启用真实资金。

## 产品和业务影响

### 乘车人

- 订单只展示总价、费用明细、退款和责任规则，不展示内部 `15%/45%/40%` 商业分成。
- 发票主体、退款主体和客服责任必须与最终法律关系一致。
- 不得因运营主体或车主内部结算失败影响依法应得退款和安全处理。

### 车主

- 接单前必须明确当前归属运营主体和适用分成规则。
- 订单完成后可查看车主应得金额、法定扣缴、付款状态和异常原因。
- 车主付款手续费不得从 `40%` 中扣除。
- 运营主体不能通过后台临时降低已接受订单的车主份额。

### 运营主体

- 获得订单可分配金额的 `45%` 经济份额。
- 承担车主管理、车主付款、付款手续费、合同和必要税务责任。
- 需要完成逐订单、逐车主和逐结算批次对账。
- 需要承担退款回退、余额不足、付款失败和退出迁移的运营责任。

### 平台

- 获得订单可分配金额的 `15%` 毛服务费。
- 承担支付手续费、支付协调、平台账务、对账、风控和系统责任。
- 不得因承担支付手续费而减少运营主体或车主份额。
- 需要建立运营主体准入、暂停、退出、结算和风险案件能力。

## 安全、隐私、合规与公平性影响

- 平台和运营主体的收款账户、商户号、法人和税务资料属于高敏感企业及资金数据。
- 车主收款账户必须由持牌支付机构或受控供应商验证，App 和普通后台不保存完整支付凭据。
- 分成规则变更必须双人复核、版本化、未来生效和完整审计。
- 禁止以性别、头像、年龄、民族、残障、互动偏好或投诉行为差异化设置分成比例、结算时效或手续费。
- 运营主体暂停和资金冻结必须有原因码、范围、期限、复核和申诉路径。
- 该模式不能作为规避道路运输、劳动用工、税收征管、反洗钱、消费者权益保护或支付监管的工具。

## 验收标准

- 多运营主体资金实现开始前，复式账本表、迁移、Repository、数据库借贷平衡约束、只追加冲正、余额重建和资金对账阻断已经验收通过。
- 任意订单的 `platform_share + operator_share + driver_share` 严格等于 `allocable_fare_minor`。
- `15%/45%/40%` 使用整数最小货币单位计算，不出现浮点误差。
- 尾差只进入车主份额并记录规则版本。
- 支付手续费只进入平台费用，不减少运营主体和车主应得金额。
- 车主付款手续费只进入运营主体费用，不减少车主应付款。
- 一笔订单只能绑定一个运营主体分成快照。
- 车主更换运营主体不会改变历史订单。
- 运营主体收到 `85%` 后，车主 `40%` 应付款仍保持开放，直到车主付款确认成功。
- 分配、付款、退款、退分账和冲正使用独立幂等请求和账本交易。
- 任何非零对账差异会阻止相关主体结算、付款和账务日关闭。
- 后台不存在直接修改余额、历史比例或车主应得金额的入口。
- 所有真实能力门禁关闭时，合成分配计算不会触发真实支付机构请求。

## 生效与退出条件

本决策只有在以下条件全部满足后才能从 `评审中` 变更为 `已批准`：

- 法律负责人确认平台、运营主体、乘车人和车主的合同及运输经营责任。
- 财务和税务负责人确认总额或净额收入、发票、税费和代扣代缴方案。
- 至少一家持牌支付机构书面确认平台、二级商户、佣金、退款、回退、付款、账单和对账能力满足设计。
- 每个运营主体的商户、收款、付款、余额不足和退出责任可被合同和系统执行。
- 合成资金内核通过分配、退款、冲正、付款失败、并发和对账测试。

以下任一情况触发退出或重新评审：

- 法律意见认定平台必须直接承担全部运输服务和车主付款责任。
- 支付机构不能支持运营主体作为合规收款主体或不能提供可靠退款回退。
- 会计政策要求的资金和收入路径与当前两层模型实质冲突。
- 运营主体无法持续承担车主付款、税务、退款或安全责任。
- 业务决定改变 `15%/45%/40%` 或手续费承担主体。
