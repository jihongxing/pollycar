# 决策 0020：运营后台账号认证与工作身份会话

## 决策状态

- 状态：`实施前设计已冻结；已批准内部沙箱合成代码实现`
- 实施批准日期：`2026-07-15`
- 冻结日期：`2026-07-15`
- 适用环境：内部沙箱与合成数据
- 默认门禁：`synthetic_admin_authentication=false`
- 真实后台账号：禁止
- 生产认证与生产后台：禁止

## 背景与待解决问题

运营控制台阶段一已经冻结“内部用户、组织成员关系、功能角色、作用域、服务端组织上下文、统一授权和追加式审计”，但当前后台仍缺少可供正式运营使用的账号入口。若在编码阶段临时决定注册方式、组织归属、MFA、会话和身份切换规则，将导致共享账号、跨主体越权、前端伪切换、离职会话残留和认证审计断裂。

本决策冻结后台账号从邀请到离职的完整认证边界，并已批准在默认关闭门禁后使用合成账号、合成凭据和内存状态完成内部沙箱实现。它不批准真实邮箱、真实员工数据、真实身份提供商或生产认证实现。

## 决策目标与非目标

目标：

- 一个自然人只有一个内部用户和一个后台认证账号；
- 一个自然人可以通过多个组织成员关系承担不同工作职责；
- 单个会话只绑定一个工作身份，不合并多个组织权限；
- 平台人员与运营公司人员在产品入口、范围和会话上明确隔离；
- 邀请、登录、MFA、恢复、身份切换和撤销均可服务端判定并完整审计。

非目标：

- 不开放公众注册；
- 不建立运营公司独立账号系统；
- 不在本决策冻结完整业务角色权限矩阵；
- 不批准真实邮件、真实人员数据或生产启用；
- 不替代阶段一的组织授权和审计事实源。

## 可选方案及权衡

### 方案一：公众注册后由管理员补充权限

否决。后台账号不是消费者账号，公众注册会扩大攻击面，并产生无组织归属、未完成审查和长期悬空账号。

### 方案二：每个运营公司建立独立账号系统

否决。该方案会形成多个认证事实源，难以统一撤销、审计、MFA 策略和跨组织任职。

### 方案三：统一账号并在前端切换当前组织

否决。只修改前端状态不能撤销旧权限，也无法证明服务端每次请求使用了唯一工作身份。

### 方案四：统一内部用户、单一认证账号、多个成员关系、单会话单工作身份

采用。该方案复用阶段一授权模型，同时让认证、组织任职和业务权限保持独立。

## 最终决策

采用以下唯一模型：

```text
统一内部用户
+ 一对一后台认证账号
+ 多个组织成员关系
+ 单会话单工作身份
+ 工作邮箱与密码
+ 强制 TOTP
+ 旋转刷新令牌
+ 服务端统一授权与追加式审计
```

编码阶段不得替换为公众注册、共享账号、短信唯一 MFA、前端身份切换、多组织合并会话或运营公司独立账号系统。

## 核心对象

### 内部用户

- `internal_user` 表示唯一自然人；
- 不直接持有组织权限；
- 与产品用户账号隔离；
- 不因加入多个组织而复制自然人记录。

### 后台认证账号

- `admin_account` 与 `internal_user` 一对一；
- 保存后台认证生命周期，不保存业务角色；
- 唯一登录标识为规范化工作邮箱；
- 同一规范化工作邮箱只能对应一个后台账号；
- 账号状态固定为：

```text
invited
→ pending_activation
→ active
→ locked
→ active
→ suspended
→ active
→ departed

active
→ revoked
```

- `departed` 与 `revoked` 为终态；
- 终态账号不得直接恢复；
- 重新入职必须创建新的组织成员关系并重新邀请，经独立审批后关联原自然人。

### 组织成员关系

- 继续复用阶段一 `organization_membership`；
- 单个成员关系只连接一个用户和一个组织；
- 组织类型仅允许 `platform` 或 `operator`；
- 原有 `governance` 上下文只作为平台内部治理用途，不形成第三类产品账号；
- 成员关系状态固定为 `invited`、`active`、`suspended`、`departed`、`revoked`；
- `departed` 与 `revoked` 为终态；
- 成员关系、角色或作用域变化必须撤销受影响工作身份的全部会话。

### 工作身份

- `work_identity` 是会话选择结果，不是新的权限事实源；
- 固定由一个有效 `membership_id`、该成员关系的角色绑定、作用域绑定和会话用途组成；
- 产品层只展示“平台工作身份”和“运营公司工作身份”；
- 一个会话只能绑定一个工作身份；
- 平台工作身份可在已授权的城市和运营主体观察范围内缩小或切换观察范围，但不能改变角色和最高数据等级；
- 运营公司工作身份的 `operator_id` 固定，不能切换到其他运营公司；
- 切换工作身份必须服务端重新授权、签发新会话并使旧访问令牌失效。

## 邀请与激活

后台不提供公众注册，唯一流程为：

```text
管理员创建邀请
→ 工作邮箱验证
→ 设置密码
→ 登记 TOTP
→ 保存恢复码
→ 确认组织和初始角色摘要
→ 激活账号与成员关系
→ 登录并选择工作身份
```

邀请规则：

- 邀请按规范化工作邮箱发送；
- 邀请令牌单次使用，默认有效期为 `PT72H`；
- 服务端只保存邀请令牌摘要；
- 重发邀请必须立即撤销旧邀请；
- 平台授权人员可在批准范围内邀请平台或指定运营公司成员；
- 运营公司授权人员只能邀请本公司成员；
- 邀请不得扩大邀请人的组织、角色和作用域边界；
- 邀请接受前必须再次验证成员关系、角色批准和组织状态；
- 已过期、已撤销、已使用或摘要不匹配的邀请必须拒绝；
- 邀请激活不能自动启用任何生产能力。

## 密码与多因素验证

登录方式固定为：

```text
工作邮箱 + 密码 + TOTP
```

密码规则：

- 最少 `14` 个字符；
- 禁止常见密码和已泄露密码；
- 服务端使用 `Argon2id` 保存密码摘要；
- 不记录密码原文、密码提示或可逆密文；
- 密码重置后撤销该账号全部会话。

MFA 规则：

- TOTP 为所有后台账号强制第二因素；
- 不使用短信验证码作为后台 MFA；
- 激活前必须完成 TOTP 登记和首次验证；
- TOTP 验证码不得在有效窗口内重复使用；
- 每次登记生成一次性恢复码，恢复码只显示一次且只保存摘要；
- 使用恢复码后立即作废该恢复码；
- MFA 重置必须由与申请人不同的授权平台管理员批准；
- MFA 重置后撤销全部会话，并要求重新登记 TOTP；
- 高风险操作要求最近 `PT15M` 内完成 MFA，超时必须重新验证。

## 登录、锁定与恢复

- 登录响应不得区分邮箱不存在、账号不可用或密码错误；
- 连续 `5` 次失败认证后账号进入 `locked`；
- 自动锁定时间为 `PT30M`，期间所有密码和 TOTP 登录尝试均拒绝；
- 成功登录清零失败计数；
- `suspended`、`departed` 和 `revoked` 账号不得登录；
- 密码恢复必须通过单次、摘要存储、有效期 `PT30M` 的恢复令牌；
- 密码恢复不替代 MFA；无法使用 TOTP 或恢复码时必须进入独立 MFA 重置流程；
- 账号恢复不得恢复已终止成员关系。

## 会话

- Access Token 有效期固定为 `PT15M`；
- 刷新会话绝对有效期固定为 `PT8H`；
- 空闲超时固定为 `PT30M`；
- 不提供“记住我”；
- 单个账号最多保留 `3` 个活动会话，超过时撤销最旧会话；
- 刷新令牌每次使用后轮换，服务端只保存摘要；
- 旧刷新令牌再次出现视为重放，必须撤销整个 `session_family`；
- Web 会话使用 `HttpOnly`、`Secure`、`SameSite=Strict` Cookie，并要求 CSRF 防护；
- 会话必须绑定账号、成员关系、工作身份、会话族、认证时间、MFA 时间和设备摘要；
- 设备摘要不得作为单独认证因素；
- 账号锁定、暂停、离职、撤销、密码重置和 MFA 重置必须撤销全部会话；
- 成员关系、角色或作用域变化必须撤销受影响工作身份会话；
- 服务端必须在每个请求重新确认账号、成员关系、工作身份、会话和功能门禁仍有效。

## 授权与职责分离

- 邀请创建者不得批准自己的高权限成员关系；
- 运营公司管理员不得邀请、激活、暂停或恢复其他运营公司成员；
- MFA 重置申请人和批准人必须不同；
- 平台身份管理员不得通过身份管理流程授予自己新角色或扩大自身作用域；
- 审计员只读，不得创建邀请、重置 MFA、撤销他人账号或修改成员关系；
- 技术运维只能处理技术恢复，不得代替业务负责人决定成员关系和角色；
- 完整平台与运营公司角色权限矩阵在重构第二项冻结，本决策中的职责分离不得被该矩阵放宽。

## 审计

下列事件必须写入阶段一追加式审计：

- 邀请创建、重发、撤销、过期和接受；
- 账号激活、锁定、解锁、暂停、离职和撤销；
- 登录成功、登录失败和 MFA 失败；
- MFA 登记、恢复码使用、重置申请和重置批准；
- 会话签发、刷新、轮换、重放撤销、主动退出和管理员撤销；
- 工作身份选择、切换、拒绝和范围变更；
- 成员关系、角色和作用域变化导致的会话撤销；
- 所有允许与拒绝的身份管理操作。

审计严禁记录密码、密码摘要、TOTP 秘钥、TOTP 验证码、恢复码、邀请令牌、密码恢复令牌、Access Token、刷新令牌或 Cookie 原文。

## 产品和业务影响

- 后台用户入口从“合成身份选择器”升级为邀请制账号流程；
- 平台人员和运营公司人员共享统一认证入口，但进入不同工作身份；
- 菜单和业务权限继续由后续角色权限矩阵与服务端授权导航决定；
- 账号认证成功不等于拥有业务模块权限。

## 安全、隐私、合规与公平性影响

- 工作邮箱属于内部人员信息，只能用于账号识别、通知和安全审计；
- 不采集个人手机号作为后台登录或 MFA 必填项；
- 认证秘密必须使用专用密钥和秘密管理能力保护；
- 所有认证响应采用通用错误语义，降低账号枚举风险；
- 离职和撤销必须形成组织流程与系统会话撤销闭环；
- 生产启用前仍需完成真实企业身份、邮件供应商、员工数据、保留期限、删除和事件响应评审。

## 验收标准

- 机器契约和 JSON Schema 通过；
- 至少三十二项邀请、登录、MFA、会话、身份选择、撤销和审计场景通过；
- 门禁默认关闭且依赖失败时关闭；
- 无邀请不能注册；
- 单个会话不能合并平台和运营公司权限；
- 运营公司身份不能扩大到其他运营公司；
- 刷新令牌重放撤销整个会话族；
- 成员关系和账号失效后旧会话立即失效；
- 审计中不包含任何认证秘密原文；
- 未获单独批准前不存在认证运行时代码、真实邮件和生产启用。

## 生效与退出条件

本决策在文档、机器契约、Schema、验收场景和专项治理检查全部通过后成为实现前冻结基线。

进入代码实现必须由决策人再次明确批准，并继续满足：

- `synthetic_admin_authentication=false` 默认关闭；
- 仅内部沙箱和合成账号；
- `real_admin_organization_accounts=false`；
- `production_authentication=false`；
- `production_admin_enabled=false`。

真实账号或生产认证必须创建新的高风险批准，不得以本决策自动放行。
