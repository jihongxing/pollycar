# 0026 生产能力门禁统一模型

## 状态

已批准。

## 日期

2026-07-25。

## 背景

PollyCar 正从内部沙箱进入正式产品准备阶段。现有门禁分散在路线图、平台规范、TypeScript 契约、领域规范和验证脚本中，部分能力只存在于路线图或专项规范，部分真实身份能力已经进入运行时契约但未出现在路线图摘要。

单个布尔值无法区分能力已经实现、已经获得批准、已经完成正式配置和已经在目标环境启用。直接将一批布尔值改为 `true` 会掩盖外部批准、密钥、正式标识、数据边界、灰度和回滚尚未完成的事实。

## 决策

1. `spec/platform/feature-gates.yaml` 是生产能力门禁的唯一机器事实源。
2. `ROADMAP.md` 只保留便于人工阅读的当前有效状态摘要，不承担运行时配置职责。
3. `packages/contracts/src/feature-gates.ts` 是运行时类型和依赖解析契约，必须通过自动检查与规范保持一致。
4. 每项生产能力使用 `implemented`、`approved`、`configured` 和 `enabled` 四个独立维度描述。
5. 现有布尔门禁继续表示最终有效启用值。只有四个维度全部满足且依赖门禁有效时，运行时结果才可以为 `true`。
6. 批准证据必须包含批准编号、批准角色、批准日期、适用环境和证据引用；有期限的批准必须记录到期日。
7. 批准角色按生产决策、数据隐私、身份认证、地图供应商、运营和资金六类管理。任何代码提交、环境变量或单人操作都不能替代所需批准。
8. 首个正式产品范围包括真实数据、真实短信和手机号、正式认证、真实后台账号、基础地图、高德 SDK、高德 Web Service 和前台设备定位。
9. 首个正式产品明确排除真实支付、结算、提现、提前结算、付费弹性资格、后台定位和车辆实时位置流。
10. 所有真实能力在批准、配置和启用证据完成前继续保持失败关闭。

## 影响

- 新增或修改门禁时必须同时更新平台规范、运行时契约、依赖测试和路线图摘要。
- 正式化工作可以分别推进实现、批准和配置，不再通过提前打开开关表示进度。
- 内部沙箱和合成能力可以继续用于开发验证，但不得被解释为真实生产能力已经批准。
- 真实支付、身份、生物识别、后台定位和真实资金能力仍需各自的专项决策和启用评审。

## 批准角色

- 产品与生产决策负责人；
- 安全负责人；
- 隐私负责人；
- 身份合规负责人；
- 地图供应商负责人；
- 运营负责人；
- 财务负责人；
- 法律负责人。

## 验证要求

- 规范、TypeScript 契约和路线图中的门禁名称必须自动对齐；
- 所有真实能力的默认有效值必须为 `false`；
- `internal_sandbox` 是唯一默认有效值为 `true` 的环境门禁；
- 缺少任何批准、配置、依赖或显式启用时必须失败关闭；
- 修改本文档和平台规范后必须通过文档治理、生产契约和门禁对齐检查。
