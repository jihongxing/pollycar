# 决策编号：0024 乘客与车主认证流程重构方案

## 决策状态

- 状态：已批准合成实现
- 是否允许生产启用：否
- 是否允许代码实现：仅允许合成、沙箱、关闭态和不连接真实身份数据的实现
- 推荐范围：直接进入 UI 原型、合成流程和适配层实现；真实供应商评估与接入另行批准
- 负责人：产品负责人、工程负责人、安全与隐私负责人、运营负责人

本文批准的是认证流程和合成实现方向，不代表真实身份、真实生物信息、真实车辆材料或外部供应商已经批准接入。

## 背景与待解决问题

当前乘客认证和车主认证已经具备基本业务闭环：

- 乘客侧支持授权、开始自动核验、查询结果、失败重试和申诉。
- 车主侧支持车主资料、车辆信息、保险信息、材料提交、审核中、补材料和审核通过。
- 服务端、App 和测试均以合成数据及内部沙箱为主。

当前主要问题不是缺少功能，而是缺少成熟产品应有的认证体验和自动化执行能力：

1. 页面主要围绕表单、状态和接口动作组织，用户不容易理解认证目的、准备事项和下一步。
2. 乘客认证尚未真正启动第三方身份核验、证件识别、活体或人脸比对流程。
3. 车主认证仍以人工提交和审核为主，车辆、保险和资格材料缺少自动识别、校验和预审。
4. 自动化失败、供应商超时、回调丢失、结果不确定和人工复核之间缺少统一的用户恢复路径。
5. 供应商能力、PollyCar 业务规则和运营人工判断的责任边界尚未冻结。

## 决策目标与非目标

### 决策目标

- 将乘客认证和车主认证设计为两个清晰、可恢复、可追踪的用户任务。
- 保持一个 App、一个账户和乘客／车主显式身份切换。
- 用稳定的 PollyCar 业务状态隔离第三方供应商状态和技术实现。
- 默认自动化处理标准路径，仅将异常、冲突或高风险情况转人工。
- 明确第三方组件、PollyCar 服务、运营人员和最终决策人的责任边界。
- 为后续供应商调研、UI 原型、契约实现和移动端验收提供统一基线。

### 非目标

- 本方案不选择具体供应商。
- 本方案不批准真实身份、真实生物信息、真实车辆材料或生产数据库接入。
- 本方案不改变现行车辆准入阈值、身份披露规则、权限规则或生产启用门禁。
- 本方案不把第三方返回结果直接等同于 PollyCar 的最终业务资格。
- 本方案不以“通过测试”替代法律、隐私、安全、公平性和业务负责人签署。

## 最终决策

采用“平台最终裁决、第三方只提供信号”的最小方案。

### 乘客认证

- 使用一个可替换的身份核验适配层，优先覆盖证件采集、OCR、活体和人脸比对。
- 第三方只返回单项检查结果、追踪编号和处理状态。
- PollyCar 服务端负责授权、认证状态、重试、处理中、结果未知、申诉和访问权限。
- 乘客是否通过认证、是否允许继续使用乘客功能，必须由 PollyCar 服务端决定。

### 车主认证

- 复用乘客认证结果，不要求用户重复完整身份认证。
- 车主材料先只实现最小自动化：材料上传、基础 OCR、有效期识别、字段一致性检查。
- 不建设复杂的供应商评分或全自动风控；材料冲突、保险责任、车辆照片和异常情况进入 PollyCar 人工审核。
- 车主是否通过审核、是否可以切换车主身份、是否可以接单，必须由 PollyCar 服务端决定。

### 平台裁决原则

第三方结果只能进入 `provider_signal`，不得直接修改认证状态、身份权限、车主资格、接单资格或配额。

平台服务端必须按自己的规则执行：

1. 收集并验证授权。
2. 创建和关闭认证任务。
3. 接收、验证和幂等处理第三方结果。
4. 聚合检查结果、材料状态和人工审核结果。
5. 生成最终业务决定。
6. 授予、保持、暂停、撤销或拒绝对应功能权限。

### 成本与复杂度约束

- 第一阶段只保留一个身份核验适配接口，不在代码中绑定供应商品牌。
- 车主材料只做 OCR、有效期和字段一致性，不先做车辆联网核验、保险自动裁决或复杂反欺诈。
- 只保留必要的结果字段和供应商追踪编号，不长期保存原始身份或生物材料。
- 第三方不可用时不自动放行，进入处理中、重试或人工审核。
- 供应商调研矩阵作为后续取证参考，不再阻塞 UI 原型和合成实现。

## 统一产品原则

### 用户看到的是任务，不是内部状态

界面只向用户说明以下内容：

- 当前需要完成什么。
- 为什么需要完成。
- 需要准备什么。
- 当前是否正在处理。
- 如果失败，用户可以如何恢复。
- 认证完成后，哪些功能可以使用。

不得在普通业务界面展示 API 字段、供应商状态、错误码、数据库名称、内部状态机名称、审计字段或合成数据说明。

### 标准路径自动化，异常路径可解释

- 标准材料和标准结果由自动化流程完成。
- 供应商无法判断时进入“需要人工确认”，不直接显示技术失败。
- 人工复核需要明确材料、原因、处理期限和下一步。
- 异常恢复后，异常说明和补救提示应从正常页面消失。

### 认证结果与业务资格分离

身份核验通过不自动代表车主具备接单资格；车辆材料通过也不自动代表用户可以绕过身份、配额、安全和权限限制。

## 乘客认证流程

### 业务目的

确认用户满足乘车所需的实名和成年条件，并在必要范围内生成可供行程安全使用的身份结果。认证完成后，用户可以继续使用乘客功能；认证失败时，用户应能重试、补充材料或提交复核。

### 推荐步骤

| 步骤 | 用户任务 | 自动化节点 | 人工兜底 |
| --- | --- | --- | --- |
| 1. 认证说明 | 了解认证目的、所需材料、预计耗时和隐私影响 | 根据账户和地区判断需要的检查项 | 规则冲突时由运营确认适用规则 |
| 2. 授权确认 | 同意身份、必要生物特征和第三方处理说明 | 记录隐私文本版本、授权时间和授权范围 | 授权争议或撤回由隐私流程处理 |
| 3. 启动核验 | 进入第三方认证组件 | 创建一次性、短时有效的核验会话 | 会话创建失败时允许重新获取 |
| 4. 证件采集 | 按组件指引拍摄证件正反面 | OCR、证件真伪、有效期、年龄信息识别 | 识别冲突、证件异常或供应商不确定时人工复核 |
| 5. 活体与人脸 | 按指引完成活体动作 | 活体检测和人脸比对 | 多次失败、疑似冒用或结果不确定时人工复核 |
| 6. 处理等待 | 等待最终结果 | 通过回调或安全查询同步结果，支持幂等和重试 | 超时或回调缺失时由运营查看供应商追踪记录 |
| 7. 结果确认 | 查看认证完成或处理中的结果 | 将供应商结果映射为 PollyCar 业务状态 | 复核通过或拒绝后由运营记录用户可理解的原因 |
| 8. 失败恢复 | 重试、补充材料或提交复核 | 根据失败原因限制重试频率和次数 | 申诉、特殊证件或争议情况进入人工队列 |

### 乘客页面状态

| 页面状态 | 用户表达 | 主行动 |
| --- | --- | --- |
| 未开始 | “完成认证后即可继续使用乘客服务” | 了解并继续 |
| 待授权 | “请确认身份与隐私处理说明” | 同意并开始 |
| 待准备 | “请准备本人有效证件，并确保光线充足” | 开始认证 |
| 认证进行中 | “正在完成身份确认，请不要关闭页面” | 返回查看进度 |
| 处理中 | “材料已提交，结果还在确认中” | 查看最新结果 |
| 已通过 | “认证已完成，可以继续使用乘客服务” | 返回乘客首页 |
| 需要补充 | “有一项材料需要重新完成” | 重新认证 |
| 暂未通过 | “这次没有完成认证，你可以重新尝试或提交复核” | 重新尝试／提交复核 |
| 服务异常 | “认证服务暂时不可用，稍后再试” | 稍后重试 |
| 复核中 | “我们正在核对你提交的说明” | 查看进度 |

### 乘客自动化边界

第三方可以负责：

- 证件图像采集、OCR 和证件基础校验。
- 活体检测、人脸比对和供应商风险信号。
- 核验会话、结果回调和供应商追踪编号。

PollyCar 必须负责：

- 是否要求认证、检查哪些业务条件和何时允许访问乘客功能。
- 用户授权、隐私文本版本、结果保存范围和数据删除策略。
- 供应商结果到业务状态的映射。
- 重试、申诉、人工复核和最终业务资格。
- 审计、幂等、超时、降级和异常通知。

第三方不得负责：

- 直接修改 PollyCar 账户身份或乘客权限。
- 直接决定用户是否可以使用全部业务功能。
- 直接向用户展示未经过 PollyCar 产品语言转换的原始结果。

## 车主认证流程

### 业务目的

确认用户身份、驾驶及车辆材料满足当前车辆准入规则，并在自动预审和必要人工审核完成后，获得车主工作身份和接单资格。

车主认证是组合流程，不应被设计成单一“身份认证 SDK”页面。

### 推荐步骤

| 步骤 | 用户任务 | 自动化节点 | 人工兜底 |
| --- | --- | --- | --- |
| 1. 车主入口 | 了解成为车主需要完成的事项、审核范围和接单边界 | 根据当前身份和资格预检查可申请性 | 资格或权限冲突由运营处理 |
| 2. 身份确认 | 确认本人身份与账户一致 | 复用乘客身份认证结果，必要时补充活体或人脸核验 | 身份不一致、冒用或结果不确定时人工复核 |
| 3. 驾驶资格 | 提交驾驶资格所需材料 | OCR、有效期、姓名和证件号一致性检查 | 证件异常、过期、信息冲突时人工复核 |
| 4. 车辆信息 | 填写或扫描车辆基础信息 | 车牌、车辆识别信息、车型和账户信息一致性检查 | 车辆信息无法匹配时人工核验 |
| 5. 车辆材料 | 上传行驶证、车辆照片和其他必要材料 | OCR、有效期、篡改风险、重复材料和清晰度检查 | 材料缺失、疑似伪造或无法判断时人工处理 |
| 6. 保险材料 | 提交有效保险证明 | 保险有效期、责任范围和关键字段识别 | 保险责任不清、过期或承保范围有争议时人工确认 |
| 7. 自动预审 | 等待系统确认材料是否完整 | 聚合身份、资格、车辆和保险检查，给出可审核结论 | 冲突或高风险案件进入人工队列 |
| 8. 人工审核 | 在需要时补充材料或等待审核 | 自动提醒缺件、超时和材料重新提交 | 运营作出通过、补材料、拒绝或升级决定 |
| 9. 结果生效 | 了解审核结果和可接单条件 | 生成车主资格、车辆绑定和后续复审时间 | 申诉、复议、暂停、撤销和到期由运营处理 |

### 车主页面状态

| 页面状态 | 用户表达 | 主行动 |
| --- | --- | --- |
| 未申请 | “完成车主认证后，可申请开启车主工作模式” | 查看要求 |
| 准备中 | “按顺序完成身份、驾驶资格和车辆材料” | 开始申请 |
| 身份待确认 | “先确认本人身份，再继续提交车辆材料” | 完成身份确认 |
| 材料填写中 | “还有材料未完成，完成后才能提交审核” | 继续填写 |
| 自动检查中 | “正在检查材料完整性和信息一致性” | 查看进度 |
| 人工审核中 | “材料已提交，正在由专人核对” | 查看审核进度 |
| 需要补材料 | “有几项材料需要补充或重新提交” | 查看并补充 |
| 审核通过 | “车主资格已通过，可以开启车主工作模式” | 开启车主模式 |
| 审核未通过 | “暂时无法通过车主审核” | 查看原因／提交复核 |
| 已暂停 | “车主资格暂时暂停，请先处理以下事项” | 处理问题 |
| 已到期 | “部分资格或材料已到期，需要重新确认” | 更新材料 |
| 服务异常 | “审核服务暂时不可用，已保留当前进度” | 稍后重试 |

### 车主自动化边界

第三方可以负责：

- 证件采集、OCR、证件有效期和字段抽取。
- 车辆材料图像质量、字段识别和基础一致性检查。
- 保险材料字段识别和有效期提取。
- 文件安全扫描、篡改风险信号和供应商追踪记录。

PollyCar 必须负责：

- 车辆准入标准、地区规则、车辆年龄、里程、保险责任和复审周期。
- 身份与车辆的绑定、一个用户一个有效车辆等业务约束。
- 自动预审结果如何影响审核队列。
- 通过、补材料、拒绝、升级、暂停、撤销和到期等最终业务状态。
- 运营人员权限、职责分离、审计记录和申诉复议。

第三方不得负责：

- 自行决定 PollyCar 的车主工作身份是否生效。
- 绕过车辆准入规则、人工复核或安全限制。
- 直接读取或修改 PollyCar 的接单配额、身份切换权限和安全状态。

## 统一状态与供应商映射原则

后续实现不直接暴露供应商状态，而采用以下通用处理层：

1. `provider_session`：记录供应商会话和安全追踪信息。
2. `provider_signal`：记录证件、活体、OCR、保险或车辆材料等单项信号。
3. `verification_case`：聚合一次乘客或车主认证任务。
4. `business_decision`：由 PollyCar 规则和人工审核生成最终业务结论。
5. `access_grant`：仅在业务结论满足条件后授予乘客或车主功能权限。

供应商结果只能作为信号或证据来源，不能直接作为权限授予命令。

以下能力必须成为统一基础设施：

- 一次性会话和过期控制。
- 回调签名校验。
- 回调重复投递和请求重放保护。
- 状态版本和幂等键。
- 超时、重试和结果未知。
- 供应商不可用时的关闭或人工转交。
- 原始材料最小化留存和访问审计。
- 供应商切换和数据迁移退出方案。

## 页面与交互原型要求

供应商调研前，UI 原型只冻结产品任务和状态，不绑定具体供应商品牌或 SDK 视觉。

乘客认证原型至少覆盖：

- 认证说明页。
- 授权确认页。
- 第三方组件进入前的准备页。
- 认证进行中页。
- 通过、处理中、补充、失败、复核中和服务异常页面。

车主认证原型至少覆盖：

- 车主申请入口。
- 任务总览和分步进度。
- 身份确认、驾驶资格、车辆信息、保险材料和材料上传页面。
- 自动预审中页面。
- 补材料页面，定位到具体材料。
- 审核通过、未通过、暂停和到期页面。

产品化验收重点：

- 每个状态只有一个清晰主行动。
- 用户可以从失败状态恢复到具体任务。
- 正常路径不持续展示限制、内部规则和技术实现。
- 移动端 390×844 和 430×932 不出现横向溢出、遮挡、裁切或不可操作控件。
- 认证组件退出、返回、超时和网络中断后，用户可以回到 PollyCar 并看到正确进度。

## 可选方案及权衡

### 方案 A：继续自建全部认证能力

- 优点：可控性高，供应商依赖少。
- 缺点：证件识别、活体、反欺诈、合规和持续维护成本极高。
- 结论：不推荐作为当前阶段方案。

### 方案 B：单一第三方包办乘客和车主全部认证

- 优点：接入速度快，供应商接口统一。
- 缺点：供应商能力与 PollyCar 车辆准入规则不完全匹配，存在供应商锁定和责任边界风险。
- 结论：不推荐作为完整方案，可作为局部能力候选。

### 方案 C：第三方负责可验证信号，PollyCar 负责业务决策

- 优点：自动化与业务规则解耦，可保留人工兜底和供应商替换能力。
- 缺点：需要建设适配层、案件聚合、回调治理和审核队列。
- 结论：推荐方案。

### 方案 D：全部由人工审核

- 优点：初期规则灵活，供应商依赖少。
- 缺点：处理成本高、体验慢、一致性和规模化能力差。
- 结论：仅作为异常和高风险兜底，不作为标准路径。

## 分阶段实施顺序

### 阶段一：流程和契约冻结

- 冻结乘客和车主的步骤、页面状态、用户文案和主行动。
- 明确供应商信号、PollyCar 业务状态和人工决策的边界。
- 补充 `spec/` 中认证会话、状态、权限、回调和错误恢复契约。
- 保持真实能力关闭，仅使用合成供应商验证流程。

### 阶段二：最小供应商验证

- 只验证一个身份核验候选在沙箱中的会话、回调和失败路径。
- 只验证车主材料 OCR、有效期和字段一致性，不承诺自动通过。
- 不因公开资料、销售演示或沙箱通过而批准真实接入。
- 供应商能力矩阵保留为后续替换和采购时的证据清单，不作为原型和合成实现的前置阻断。

### 阶段三：UI 原型与移动端验收

- 基于本方案制作乘客和车主认证高保真原型。
- 覆盖正常、空、加载、处理中、补材料、失败、恢复和复核路径。
- 使用现有设计令牌，不把第三方 SDK 的视觉直接当作 PollyCar 产品界面。
- 在代表性移动视口完成页面级检查。

### 阶段四：沙箱自动化接入

- 先实现供应商适配器、会话、回调、幂等、超时、重试和人工转交。
- 使用可控的合成供应商或供应商沙箱，不接入真实身份数据。
- 增加契约测试、异常场景测试、权限测试和审计验证。
- 通过后仍保持真实供应商生产能力关闭。

### 阶段五：真实能力评审与灰度

- 完成法律、隐私、安全、公平性、运营和工程评审。
- 确认数据处理、留存、删除、供应商责任和事故响应。
- 明确灰度对象、监控指标、人工接管、回滚和退出条件。
- 只有获得明确批准后，才进入真实能力和生产启用阶段。

## 验收标准

### 产品流程

- 乘客和车主都能从入口理解目的、准备事项和预计下一步。
- 所有标准路径都有明确的完成结果。
- 所有失败状态都有可执行的恢复路径。
- 处理中状态不会要求用户重复提交，也不会丢失当前进度。
- 车主补材料能定位到具体材料，不要求重新填写全部表单。

### 自动化

- 标准乘客认证可以由第三方会话驱动完成，并正确映射到 PollyCar 业务状态。
- 标准车主材料可以自动完成字段提取、基础校验和预审分流。
- 供应商回调重复、延迟、丢失、签名错误和结果未知均有可验证处理。
- 供应商不可用时不会错误授予认证资格。
- PollyCar 业务规则不会被供应商结果绕过。

### 安全与治理

- 未授权用户无法创建或查看他人的认证任务。
- 真实身份和生物数据默认关闭，沙箱不会写入真实数据。
- 原始材料和供应商追踪信息按最小权限访问并记录审计。
- 人工审核、复核、撤销和升级具备职责分离。
- 生产启用前完成法律、隐私、安全、公平性和业务负责人签署。

### 移动端产品化

- 在 390×844 和 430×932 视口检查乘客认证和车主认证的代表性状态。
- 页面无横向溢出、控件遮挡、文字裁切、焦点丢失和不可恢复的返回路径。
- 页面不展示接口字段、内部状态、供应商原始文案或仅供验收使用的说明。
- 认证组件退出或系统中断后，用户能够回到正确的 PollyCar 页面。

## 生效与退出条件

### 生效条件

本方案的合成实现已经批准；真实能力仍需满足以下条件后才可进入单独评审：

- 产品负责人确认流程和页面状态。
- 工程负责人确认契约、适配层和故障恢复方案。
- 安全与隐私负责人确认数据边界、授权、留存、删除和审计方案。
- 运营负责人确认人工队列、审核规则、复核和升级机制。
- 供应商书面材料、数据处理协议、删除证明和退出方案完成。

转为“已批准”前，不得启用真实身份、真实生物信息、真实车辆材料或生产认证。

### 退出条件

如果供应商无法满足数据处理、回调可靠性、删除证明、审计、地区可用性或退出要求，则不得接入该供应商；流程应回退到合成沙箱或人工关闭态。

如果自动化误判率、人工积压、回调丢失、错误授予资格或用户无法恢复等指标超过评审阈值，应立即关闭真实自动化入口并保留人工处理能力。
