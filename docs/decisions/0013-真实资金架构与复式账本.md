# 决策 0013：真实资金架构与复式账本

## 决策状态

`已批准`

- 批准范围：`供应商中立机器契约、合成资金适配器、复式账本和对账内核`
- 生产启用结论：`尚不能批准`
- 收敛日期：`2026-07-13`
- 关联评审：`docs/reviews/0005-真实资金架构评审.md`
- 限制：允许在 `real_payment: false` 下建立供应商中立契约、合成支付适配器、复式账本和对账内核；禁止调用真实支付机构、写入真实资金数据或开放真实资金入口。

## 背景与待解决问题

现有系统已经实现零金额支付前置和真实能力默认关闭，但零金额状态不能证明真实金额正确，也不能承担退款、分账、提现、拒付和对账责任。真实资金能力必须先确定：

- 平台是否自行保管资金。
- 金额由谁计算和锁定。
- 支付、行程和账务是否使用独立状态。
- 如何防止重复扣款、退款、分账和提现。
- 如何记录资金归属。
- 如何与支付机构和银行流水对账。
- 如何处置未知结果、孤立资金和人工调整。

## 决策目标与非目标

目标：

- 建立金额正确、请求合法、账本平衡、对账闭环的统一资金架构。
- 将内部可决定事项收敛为确定规则。
- 将必须由外部机构或专业负责人确认的事项收敛为明确阻断证据。
- 允许先实现不接触真实资金的生产级内核。

非目标：

- 不在本决策中选择具体支付供应商。
- 不批准真实支付、分账、绑卡或提现。
- 不建立平台储值钱包。
- 不在本决策中确定服务费比例、多运营主体分成、税率或最终会计政策；后续专项决策可以在不改变本架构原则的前提下补充。
- 不以技术评审替代法律、财务、税务和持牌支付机构书面结论。

## 可选方案及权衡

### 方案 A：平台自行保管资金并维护用户余额

优点：

- 产品控制力强。
- 可以自主安排退款、结算和提现。

缺点：

- 显著扩大资金监管、备付金、账户体系、反洗钱、清算、审计和安全责任。
- 平台余额容易被理解为储值或资金池。
- 与当前“不建立钱包和储值”的产品边界冲突。

结论：否决。

### 方案 B：完全依赖支付机构记录，不建立内部复式账本

优点：

- 初期开发量较小。
- 支付机构承担部分资金事实记录。

缺点：

- 无法独立解释待履约资金、车主应付款、平台收入、税费和手续费。
- 无法可靠处理跨供应商、退款、争议、拒付、冲正和对账差异。
- 支付机构记录不能替代平台业务责任和内部账务。

结论：否决。

### 方案 C：持牌支付机构执行外部资金动作，平台维护独立复式账本

优点：

- 平台不自行建立储值钱包或保管完整支付凭据。
- 外部支付事实与内部资金归属分离。
- 可以通过支付机构流水、内部支付聚合和复式账本完成对账。
- 支持供应商替换和异常恢复。

缺点：

- 需要更严格的支付聚合、账本、对账和运营控制。
- 需要财务、税务和法律共同批准。

结论：采用。

## 最终决策

### 资金承载模式

- 平台不建立储值钱包，不允许充值，不自行形成可自由转移的平台余额。
- 真实扣款、原路退款、分账或付款必须由具备相应能力的持牌支付机构执行。
- 平台内部维护支付聚合和复式账本，用于记录业务责任和资金归属，但内部账本不替代支付机构清算。
- 优先采用支付机构支持的平台型收款、分账或付款能力；若供应商无法满足查询、验签、退款、账单和对账要求，则不启用真实资金。
- 参考出行行业公开模式，将平台定位为行程撮合、订单管理、交易秩序和支付协助方；乘车服务责任、收款主体、支付代收角色及车主所得关系必须在正式协议中按最终经营和支付产品落定。
- 不直接复制滴滴出行、曹操出行、美团打车或 Uber 的合同表述；竞品条款只用于证明行业存在“平台管理订单、第三方提供服务、支付机构处理支付”的可行结构。

### 报价与金额

- 只有 Server 可以生成权威报价。
- App 只能提交 `quote_id`，不能提交权威支付金额。
- 报价默认有效期为 `10 分钟`。
- 报价在创建支付订单时被消费；同一报价只能创建一个有效支付订单。
- 支付订单创建后金额锁定，默认支付完成窗口为 `15 分钟`。
- 上车点、目的地、时间、人数、路线、产品等级或计价规则变化时，原报价立即失效。
- 所有金额使用最小货币单位整数；API 使用十进制整数字符串，数据库使用 `bigint`，禁止浮点运算。

### 支付与业务状态

- 行程、支付订单、支付尝试、退款单、资金分配单、运营主体清算单、车主付款单和拒付案件使用独立状态机。
- 支付成功只能来自已验签回调或 Server 主动查询的确定结果。
- 客户端支付结果不能直接改变支付状态。
- 未知支付尝试未查询清楚前，不得创建新的相同扣款尝试。
- 支付成功后才能进入匹配，但支付成功不等于行程完成或平台取得收入。

### 账本

- 复式账本是内部余额和资金归属的唯一事实源。
- 已确认外部资金变化必须对应平衡账本交易。
- 分录只追加，不允许修改或删除。
- 错误使用冲正和补充分录修复。
- 同一来源事件和交易类型只能产生一笔账本交易。
- 余额投影必须可以从全量分录重建。

### 收入、车主所得和手续费

- 平台服务费收入和车主所得只在行程完成或责任结论最终确定后确认。
- 支付成功到责任确定前，乘车人资金记入待履约负债。
- 首期真实资金候选方案中，支付手续费由平台承担并记入费用，不从车主应付款中临时扣减。
- 平台服务费和多运营主体经济分配已在 `docs/decisions/0014-平台服务费与多运营主体分成.md` 形成平台 `15%`、运营主体 `45%`、车主 `40%` 的内部候选；税费、总额或净额会计确认和正式生产使用仍需财务、税务和法律书面批准。

### 取消费

- 首次真实资金封闭试验默认不启用取消费。
- 责任确定后执行全额原路退款或按安全、争议规则冻结，不在首期试验中扣除第一档或第二档取消费。
- 取消费只有在法律、财务、税务和用户认知评审单独通过后才能启用。

### 退款

- 退款必须引用原支付订单、责任结论和可退金额。
- 累计退款不得超过支付机构确认的成功支付金额。
- 重复退款命令返回原退款单。
- 退款未知时查询原退款，不创建新的业务退款。
- 支付成功但无法关联合法订单时创建孤立支付案件，并优先走原路退款评审。

### 结算和提现

- 首选支付机构管理的分账或付款模式。
- 结算表示账务归属确认，不等于已经向车主付款。
- 安全冻结、争议、退款、拒付或对账差异存在时禁止结算和提现。
- 车主可提现金额只能从账本派生。
- 不允许客服、运营人员或开发人员直接修改车主余额。

### 拒付和坏账

- 拒付发生时保留原支付和原账本记录，创建独立拒付案件和账本交易。
- 未结算车主应付款可以按案件范围冻结。
- 已经向车主付款的金额不得在没有合同、责任和法律依据时自动形成车主负余额或自动追扣。
- 拒付责任、追偿和坏账归属必须由独立规则决定。

### 账务日和关账

- 账务时区统一为 `Asia/Shanghai`。
- 账务日为北京时间 `00:00:00` 至次日 `00:00:00`。
- 日内资金扫描每 `15 分钟`执行一次。
- 次日 `06:00` 前完成内部暂结检查。
- 获得完整支付机构账单后执行正式对账；目标在次日 `12:00` 前完成正式关账。
- 支付机构账单未到达、签名失败或存在非零金额差异时不得关账；允许保持账务日开放，不得伪造按时关闭。

### 对账

- 采用业务订单、内部支付聚合、内部复式账本和支付机构流水四方对账。
- 只要平台控制的银行账户发生真实资金变化，银行流水必须作为第五方清算核对来源。
- 实时回调核对不能替代支付机构正式账单对账。
- 任意非零金额差异都必须生成持久化差异项，并阻止相关结算、提现和关账。
- 禁止自动核销非零金额差异。

### 权限分离

- 财务经办人可以创建例外退款、补记或冲正申请。
- 独立财务复核人负责批准。
- 同一人员不能同时经办和批准同一资金动作。
- 客服只能查看脱敏状态和创建案件。
- 开发人员不得在生产环境创建财务调整。
- 审计人员保持只读。

### 数据保留

- 内部保守基线按数据类别配置，不采用一个统一期限：

| 数据类别 | 内部基线 | 处置方式 |
| --- | --- | --- |
| 账本交易、账本分录、会计凭证和年度关账证据 | 30 年 | 加密归档，禁止业务侧删除 |
| 支付、退款、结算、提现、拒付和正式对账批次 | 10 年 | 热数据转归档后保持可审计查询 |
| 支付机构及银行账单原文件、差异案件和审批证据 | 10 年 | 原文件加密保存，记录摘要和访问审计 |
| 没有发生资金效果的失败支付尝试 | 5 年 | 到期删除敏感载荷，保留最小防重和审计摘要 |
| 财务后台高风险操作日志 | 10 年 | 不可变存储，只读审计 |

- 上述期限是工程和行业惯例候选，不替代法律、财务、税务和隐私负责人的正式期限映射。
- 发生诉讼、调查、拒付或安全案件时，对关联记录执行保留暂停。
- 账户注销不能删除依法或合同必须保留的财务记录，但必须解除日常产品用途并限制访问。

## 产品和业务影响

- 首次真实资金试验不收取取消费，优先验证金额、支付、退款、账本和对账正确性。
- 乘车人支付成功后仍可能因无人接单收到原路退款。
- 车主看到的待结算和可提现金额来自账本，不来自行程页面临时计算。
- 真实资金能力需要独立资金运营和财务差异处理入口。
- 支付机构故障时，产品必须允许查询和恢复，不能鼓励用户重复付款。

## 安全、隐私、合规与公平性影响

- 平台不保存支付密码和不必要的完整银行卡信息。
- 支付机构密钥只能由 Server 密钥系统持有。
- 回调必须验签、防重放并校验金额、币种、商户号和订单引用。
- 资金权限与普通运营权限分离。
- 退款、结算和拒付不能基于性别、车辆偏好、付费等级或互动结果差异化处理。
- 平台资金法律角色、税务、车主所得和数据保留仍必须获得专业书面结论。

## 验收标准

- App 篡改金额不能改变支付订单。
- 同一报价不能创建两个有效支付订单。
- 重复请求和回调只产生一次资金效果。
- 未知结果不会触发第二次盲目扣款。
- 每个确定资金事件都产生一笔平衡账本交易。
- 已过账分录不可修改或删除。
- 退款和结算累计金额不能超过可处置资金。
- 任意非零金额对账差异阻止关账和后续资金动作。
- 经办人不能批准自己的资金调整。
- 真实资金门禁关闭时，所有真实供应商调用均被 Server 阻断。

## 生效与退出条件

批准并允许实施的范围：

- 供应商中立资金契约。
- 合成支付机构适配器。
- 合成复式账本。
- 合成对账批次和差异案件。
- 真实支付默认关闭门禁。

不得生效的范围：

- 真实扣款、退款、分账、绑卡和提现。
- 真实支付机构生产密钥。
- 真实财务数据自动删除。

退出或重新评审条件：

- 需要建立平台储值钱包。
- 支付机构无法支持原路退款、查询、验签、账单或稳定唯一引用。
- 平台法律角色要求自行保管资金。
- 资金拆分、税务或车主所得模式发生实质变化。
