# 决策 0006：应用架构与领域内核工具链

## 决策状态

`已批准`

- 批准日期：`2026-07-11`
- 批准人：`项目决策人`
- 批准范围：App、后端服务和共享包组成的 pnpm workspace 工程基线。
- 限制：不批准真实数据库、支付、身份、地图、消息或生产部署集成。

## 背景与待解决问题

产品规则、状态机、事件、错误码和验收场景已形成机器规范，但尚无应用运行时、语言、包管理、测试框架、模块边界和规范同步策略。继续缺少技术决策会使首个实施包无法进入代码实现。

## 决策目标与非目标

目标：

- 让领域规则可以独立、确定性、快速测试。
- 保持业务内核不依赖数据库、网络、框架和供应商。
- 允许后续通过适配器增加 API、持久化和外部服务。
- 在 Windows 本地环境提供单一、可复现的命令入口。

非目标：

- 不选择生产数据库、云平台、支付机构和地图供应商。
- 不建立微服务、消息中间件、容器集群或复杂代码生成平台。
- 不在首包实现真实用户、资金、位置和安全案件处理。

## 可选方案及权衡

### 方案 A：TypeScript workspace + 模块化后端

优点：

- 与 YAML、JSON Schema 和 OpenAPI 工具生态匹配。
- 适合纯函数、判别联合、严格类型和快速测试。
- 可先建立领域包，后续再增加应用和基础设施适配器。

缺点：

- 必须防止领域层依赖 Web 框架和运行时细节。
- 金额、时间和并发语义需要明确值对象，不能依赖普通浮点和系统时钟。

### 方案 B：Java 或 Kotlin 分层单体

类型和并发模型成熟，但首期脚手架、构建和领域试验成本更高，当前仓库无对应工具链。

### 方案 C：Python 领域服务

原型速度快，但需要额外纪律保证状态与事件类型闭合，当前机器规范和前端共享类型收益较低。

## 最终决策

采用 TypeScript pnpm workspace。产品呈现为独立 App 和后端服务，领域内核与契约作为共享包；后端内部保持模块化单体，首个阶段只实现无资金领域包。

### 工具链

| 项目 | 决策 |
| --- | --- |
| 运行时 | Node.js 22 |
| 语言 | TypeScript，启用严格模式 |
| 包管理 | pnpm |
| 测试 | Vitest |
| 模块格式 | ESM |
| 格式与静态检查 | 首包使用 TypeScript 编译检查；代码量形成后再批准格式和 lint 工具 |
| 时间 | 注入 `Clock` 接口，生产代码不得直接读取系统时间 |
| 标识 | 注入标识生成接口，测试使用确定性标识 |
| 金额 | 整数最小货币单位，不使用浮点 |

版本规则：

- `package.json` 固定 Node.js 主版本和包管理器版本。
- 锁文件必须提交并作为依赖唯一解析依据。
- CI 和本地使用同一 pnpm 命令。
- 依赖升级作为独立变更单元，不使用无上限自动升级。

### 目录边界

```text
apps/
  app/
  server/
packages/
  domain/
    eligibility/
    quota/
    events/
    errors/
    shared/
  contracts/
  test-support/
spec/
docs/
scripts/
```

首个实施包只允许写入：

- `packages/domain/`
- `packages/domain/tests/unit/`
- `packages/domain/tests/scenarios/`
- `packages/test-support/`
- 根目录工具链配置。

`apps/app`、`apps/server` 和 `packages/contracts` 可以先建立包清单与关闭配置，但首包不得实现网络、数据库或供应商连接。

### 依赖方向

- `packages/domain` 不得依赖 `apps/*`、`packages/contracts`、Web 框架、数据库驱动或支付 SDK。
- `apps/server` 可以依赖 `packages/domain` 和 `packages/contracts`，不得绕过领域守卫。
- `apps/app` 只能依赖公开契约，不得依赖服务端领域内部实体。
- `packages/contracts` 不得依赖 `apps/*`，不得包含供应商 SDK 对象。
- 后续服务端适配器不得向领域层泄露供应商响应对象。
- 测试可以依赖领域公开 API，不得通过修改内部状态绕过转换。

### 规范同步

- YAML 规范和中文文档继续作为业务输入真相源。
- 首包采用手工实现加契约一致性测试，不直接从 YAML 生成可执行业务代码。
- 稳定标识、状态、事件和错误码可以生成只读类型或常量，但生成产物不得包含业务转换逻辑。
- 规范新增稳定标识时，一致性测试必须先失败，再更新代码映射。
- 代码不得创建规范中不存在的状态、事件或机器错误码。

### 测试策略

- 单元测试覆盖纯函数、值对象、守卫和状态转换。
- 场景测试读取或映射 `spec/tests/eligibility-scenarios.yaml` 的已批准场景。
- 所有时间测试使用可控时钟，覆盖滚动窗口边界、时区和同一自然日计数。
- 并发在首包以版本比较、重复命令和原子决策模型测试，不模拟真实数据库锁。
- 幂等测试必须证明重复命令返回原结果，不重复事件和配额占用。
- 属性式或随机测试不是首包门槛，可在基础示例稳定后评审引入。

### 最小命令

```powershell
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm test:scenarios
pnpm build
./scripts/test/preflight.ps1 -SkipProjectTests
```

首包完成后，`preflight.ps1` 应能够不带 `-SkipProjectTests` 执行类型检查、测试和构建。

## 产品和业务影响

- 允许资格和配额规则在不接触真实用户及资金的情况下进入代码验证。
- 领域内核可以被未来 API、后台任务和测试工具复用。
- 不提前锁定数据库和外部供应商，降低高风险决策变化造成的返工。

## 安全、隐私、合规与公平性影响

- 首包只使用合成数据，不处理真实身份、支付、位置、聊天和安全证据。
- 不实现付费资格路径；相关状态只可作为冻结的规范兼容类型存在。
- 领域层不得记录敏感原文或供应商错误响应。
- 公平性指标仅定义计算接口，不在无数据来源时生成结论。

## 验收标准

- `packages/domain` 无运行时网络、数据库和供应商 SDK 依赖。
- TypeScript 严格检查通过，无隐式 `any`。
- 时间和标识均可注入并在测试中确定。
- 状态、事件和错误码与机器规范保持一致。
- 配额 `3/10/15`、免费弹性 `4/12/18` 和 90 日最多启用 60 日具有边界测试。
- 付费资格路径不可被生产配置启用。
- 所有命令在 Windows PowerShell 下可执行。

## 生效与退出条件

立即对首个无资金领域内核实施包生效。

退出或替代条件：

- Node.js 或 TypeScript 无法满足性能、安全或部署需求。
- 领域规则无法在当前类型系统中清晰表达。
- 生产架构需要独立服务时，必须先证明模块边界、容量或组织约束，而非默认拆分。
