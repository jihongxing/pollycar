# 决策 0009：运营后台技术选型

## 决策状态

`已批准`

批准日期：`2026-07-11`

决策人：产品负责人、工程负责人、安全负责人

## 背景与待解决问题

运营后台需要支持桌面高密度任务、列表详情并列、字段级遮蔽、复杂确认、键盘可访问性和明暗主题。当前只批准技术基线，不批准创建后台工程。

## 决策目标与非目标

目标：

- 明确未来候选实现切片的前端边界；
- 支持严格 TypeScript 和公开契约；
- 支持任务、权限、字段披露和审计体验；
- 避免引入万能管理框架。

非目标：

- 不批准立即实现；
- 不选择部署、SSO 或生产监控供应商；
- 不接入真实数据。

## 可选方案及权衡

### React 与 Vite

优点：

- 与 App 和 Contracts 的 TypeScript 工具链一致；
- 桌面 Web、可访问性和测试生态成熟；
- 可按任务模块组织，不依赖后台模板。

缺点：

- 需要自行建立高密度组件和安全交互；
- 必须约束避免组件库默认样式主导产品设计。

### Next.js 全栈框架

优点：

- 路由、服务端渲染和全栈能力完整。

缺点：

- 内部后台首切片不需要公开 SSR；
- 容易将后台与服务端部署耦合；
- 当前增加不必要复杂度。

### 通用管理框架

优点：

- CRUD 页面搭建快。

缺点：

- 容易以资源表替代角色任务；
- 字段披露、职责分离和复杂状态难以正确表达；
- 与当前安全要求冲突。

## 最终决策

未来若实现，采用：

- React 19；
- Vite；
- TypeScript 严格模式；
- TanStack Router；
- TanStack Query；
- React Hook Form；
- React Aria 的可访问交互原语，按需使用；
- Vitest 与 Testing Library；
- Playwright 作为桌面端到端候选；
- 自有设计令牌和领域组件。

首切片不引入大型数据网格。优先使用语义表格、任务列表与详情面板；只有性能和交互实测证明需要时再评审专用网格。

不得使用通用管理员模板直接生成产品页面。

## 产品和业务影响

- 未来可以与 App 共享 Contracts 和部分语义令牌；
- 后台保持独立桌面信息架构；
- 不因技术选型批准而自动进入代码实现。

## 安全、隐私、合规与公平性影响

- 所有权限和披露由 Server 决定；
- 前端遮蔽不替代服务端字段过滤；
- 不持久化严格受限原文；
- 技术运维界面不包含业务决定组件；
- 不以审核速度排名推动草率决定。

## 验收标准

- 技术基线支持桌面三栏布局、明暗主题和键盘导航；
- 可实现字段级披露与临时授权；
- 后台只依赖公开契约；
- 无万能管理员角色或通用 CRUD 生成器；
- 代码实现仍受独立准入评审控制。

## 生效与退出条件

本决策立即作为未来技术基线生效，但不批准创建后台工程。

若可访问性、性能、安全或团队维护成本不满足要求，必须在实现前替代本决策。
