# 决策 0004：支付、退款与取消责任

## 决策状态

`已批准`

- 批准日期：`2026-07-11`
- 批准人：`项目决策人`
- 批准范围：零金额测试责任模型和真实资金业务规则基线。
- 限制：真实资金能力继续禁止启用，直到支付机构、法律、税务、发票、账务、分账、退款时效和资金安全评审全部通过。

## 背景与待解决问题

产品必须在订单进入匹配前完成支付前置门禁，避免车主接受后才发现支付失败。零金额测试和真实资金使用同一业务顺序，但资金动作不同；同时需要对无人接单、取消、安全终止、退款和申诉执行一致责任规则。

## 决策目标与非目标

目标：

- 明确预授权、扣款、释放、退款、分账和争议流程。
- 用责任分类约束爽约，同时避免对无责方收费。
- 保证资金变化幂等、可对账、可审计和可恢复。

非目标：

- 不建立钱包、储值或平台内余额。
- 不用复杂取消费最大化收入。
- 不以罚款替代安全处置和申诉。

## 可选方案及权衡

### 方案 A：匹配前全额支付

资金确定性最高，车主接受前不存在乘客支付失败；但无人接单需要退款，增加退款时效、资金占用和对账压力。

### 方案 B：发单预授权，接受或完成后扣款

兼顾支付保障和无人接单不扣款，但依赖支付机构能力和有效期管理。

### 方案 C：接受后再支付

乘客体验简单，但车主接受后支付失败会造成履约损失。

决定采用方案 A。支付必须前置是核心产品不变量，不能退化为“先匹配、后补支付”。

## 最终决策

### 通用支付前置不变量

- 订单创建分为“草稿”和“可匹配订单”；只有支付前置门禁成功后才能进入等待车主回应。
- 价格、取消责任、退款方式和预计退款时效必须在乘客确认支付前展示。
- 支付未完成、状态未知、超时或校验失败时，订单不得展示给任何车主。
- 车主接受后不得要求乘客补充首笔行程款，也不得因平台支付故障要求线下付款。
- 订单金额在支付确认后锁定；范围、路线或产品规则变化必须取消原订单并重新确认，不能静默加价。
- 所有资金操作使用独立幂等键和业务原因码，并记录订单、金额、币种、支付机构引用和状态版本。
- 平台不建立钱包、储值余额或人工改账入口。

### 零金额测试责任

零金额测试不产生真实资金流，但仍执行支付前置流程：

- 乘客确认订单后，系统创建金额为零的测试支付意图。
- 测试支付意图必须通过测试网关或内部确定性适配器返回“已支付测试态”，订单才可进入匹配。
- 禁止调用生产支付凭据、发起小额真实扣款、预授权或真实退款来模拟零金额测试。
- 测试支付失败、超时或状态未知时，订单不得进入匹配。
- 无人接单、取消和安全终止时生成零金额退款或关闭记录，用于验证状态机、幂等和审计，但不得产生金融流水。
- 零金额记录必须明确标记环境和资金模式，不能进入真实账务、税务、分账或发票流程。

零金额责任分类：

| 场景 | 测试支付结果 | 车主配额 |
| --- | --- | --- |
| 支付门禁失败或未知 | 不创建可匹配订单 | 无占用 |
| 无人接单 | 关闭测试支付，记录零金额全额退款语义 | 无占用 |
| 车主接受前乘客取消 | 关闭测试支付，记录零金额全额退款语义 | 无占用 |
| 平台原因或确认不可抗力 | 记录零金额全额退款语义 | 释放 |
| 车主责任取消或拒绝履约 | 记录零金额全额退款语义 | 计入配额并进入风险记录 |
| 乘客无正当理由取消或未出现 | 记录责任分类，不收取任何费用 | 释放 |
| 安全终止 | 暂停关闭，完成人工责任分类后记录零金额结果 | 按责任决定 |
| 正常完成 | 关闭测试支付，记录零金额完成 | 计入配额 |

零金额测试可以验证责任与状态，不得用于验证真实扣款成功率、退款到账时效、税务、发票或分账。

### 真实资金责任

真实收费启用后采用“先全额支付、后进入匹配”：

1. 乘客确认固定价格。
2. 平台创建支付意图并完成乘客全额支付。
3. 支付机构明确返回成功且平台完成验签、金额校验和幂等落账。
4. 订单才进入等待车主回应。
5. 行程完成后，将已收资金从待结算状态转入可结算状态，再执行受控分账。

支付成功不代表平台或车主已经取得最终收入；在订单完成或责任结论形成前，资金保持待退款或待结算状态。

真实资金责任分类：

| 场景 | 乘客资金处理 | 车主配额 |
| --- | --- | --- |
| 支付失败或状态未知 | 不创建可匹配订单；未知状态先查询，不重复扣款 | 无占用 |
| 无人接单 | 原路全额退款 | 无占用 |
| 车主接受前乘客取消 | 原路全额退款 | 无占用 |
| 平台原因或确认不可抗力 | 原路全额退款 | 释放 |
| 车主责任取消或拒绝履约 | 原路全额退款 | 计入配额并进入风险记录 |
| 乘客在车主出发前无正当理由取消 | 扣除固定第一档取消费，剩余原路退款 | 释放 |
| 乘客在车主到达后无正当理由取消或未出现 | 扣除固定第二档取消费，剩余原路退款 | 释放 |
| 安全终止 | 先暂停结算，人工判断责任 | 按责任决定 |
| 正常完成 | 全额转入可结算并按批准规则分账 | 计入配额 |

取消费金额在本决策中暂定为：

- 第一档：固定价格的 `10%`，最高不超过 `20 元`。
- 第二档：固定价格的 `20%`，最高不超过 `50 元`。
- 取消费不得超过订单已支付金额，不按用户属性、车辆、性别、付费等级或互动结果变化。
- 真实收费启用前必须完成用户认知、财务、税务和法律评审；若未批准具体金额，则取消费功能保持关闭并执行全额退款。

### 退款

- 全额或部分退款必须原路返回，不转入平台余额、优惠券或线下补偿替代。
- 平台应在责任自动确定后 10 分钟内提交退款；需要人工责任判断时，在结论形成后 10 分钟内提交。
- 支付机构到账时间必须在付款前和退款提交后向用户展示，平台不得承诺无法控制的即时到账。
- 退款提交失败进入有限重试和人工队列，不得通过再次扣款、负数订单或修改原流水修复。
- 重复退款请求返回同一退款结果，不得创建第二笔退款。
- 支付成功但本地订单创建失败时，系统必须自动创建“孤立支付”处置任务并优先全额退款。

### 分账与所得

- 车主所得仅在行程正常完成或责任结论明确后进入可结算。
- 安全终止、争议、支付机构拒付或退款处理中不得分账。
- 分账失败不影响乘客已支付事实，但必须阻止重复分账并进入对账队列。
- 平台服务费、车主所得、税费和支付手续费必须分别记账，不得只保存一个净额。
- 真实分账规则和比例不在本决策中批准，仍需独立财务、税务和法律结论。

### 争议与申诉

- 自动责任只能基于可验证事件：接受时间、出发状态、到达状态、取消主体、平台故障、安全事件和受控位置证据。
- 安全终止默认冻结资金结论，不自动处罚任一方。
- 用户可以申诉取消责任、退款金额和重复扣款；原责任认定人员不得单独处理申诉。
- 申诉改变责任后通过追加退款、补结算或冲正记录处理，不修改已发生资金流水。

## 产品和业务影响

- 影响发单转化、爽约率、车主参与意愿和客服争议量。
- 需要支付状态机、责任认定、退款、分账、对账和申诉后台。
- 需要处理支付超时、重复回调、部分失败和支付机构不可用。
- 全额前置支付会增加无人接单退款量，必须将退款成功率和到账投诉作为试验停止指标。

## 安全、隐私、合规与公平性影响

- 支付数据按最高敏感等级管理，不存储不必要的完整支付凭据。
- 安全事件优先于结算，不能为完成扣款强迫继续行程。
- 责任认定应基于可验证事件，不能基于用户价值或付费等级。
- 取消费、退款时限和申诉方式必须在下单前清晰披露。
- 支付、分账、税务和车主所得法律定义必须获得书面意见。
- 支付前置不得被表达为平台保证一定有车主接单；付款只使订单获得进入匹配的资格。

## 验收标准

- 支付失败、超时或未知状态时订单绝不进入匹配。
- 无人接单时已支付金额执行原路全额退款。
- 重复请求和支付回调不会重复扣款或退款。
- 车主接受前平台已经确认全额支付成功。
- 不同责任分类正确影响乘客费用和车主配额。
- 安全终止进入人工处理而非自动扣款。
- 每笔资金变化可通过订单和支付机构流水对账。
- 退款时限、失败重试和人工介入路径明确。
- 零金额模式不调用生产支付机构、不产生真实金融流水，但完整经过支付前置状态机。
- 支付成功、本地订单失败和回调乱序均有孤立支付处置场景。
- 订单金额锁定后不能静默加价或线下补收。

## 生效与退出条件

零金额测试规则内部立即生效。

零金额封闭测试生效条件：

- 测试支付适配器、支付前置状态机、幂等、乱序回调和孤立支付场景通过验收。
- 所有记录明确标记为零金额、非金融流水和测试环境。
- 责任分类、申诉和零金额退款语义完成演练。

真实资金规则仅作为实施准备基线，启用条件：

- 支付机构支持先支付、原路部分及全额退款、查询、回调验签和对账。
- 取消费、退款、分账、税务、发票、账务和车主所得法律定义获得书面批准。
- 资金隔离、清算周期、拒付、退款失败和机构故障方案批准。
- 支付状态机、幂等、并发、乱序回调、孤立支付、对账和恢复测试通过。
- 独立发布检查明确启用环境、限额、观察窗口、停止阈值和回滚负责人。

退出条件：

- 支付机构无法可靠支持先支付、原路退款、查询、验签或对账。
- 退款或争议率超过试验阈值。
- 取消费显著诱导用户进行线下协商或绕过平台。
- 无人接单导致的资金占用或退款到账体验不可接受。
