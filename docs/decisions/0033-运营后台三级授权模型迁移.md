# 决策 0033：运营后台三级授权模型迁移

## 决策状态

- 状态：已批准实施
- 批准日期：2026-07-30
- 适用环境：合成沙箱与本地验证
- 生产启用：禁止
- 替代范围：本决策替代 `0021-运营后台角色权限与授权导航.md` 中以岗位角色直接决定权限的部分；组织范围、默认拒绝、服务端授权、字段脱敏和导出复核边界继续有效。

## 背景与待解决问题

现有运营后台定义了二十余个岗位角色，并由岗位角色直接决定导航、操作、字段和导出权限。该模型超过 MVP 阶段所需复杂度，且把岗位名称、授权强度和业务能力混为一体，导致以下问题：

1. 新增岗位时需要复制权限规则；
2. 平台与运营公司的组织边界不够直观；
3. 详情记录的允许操作分散在多个领域函数中；
4. 审计、财务、技术运维等专项职责容易被误解为更高业务写权限；
5. 前端难以统一解释“无权限”“状态阻断”和“需要独立复核”。

项目尚未上线，不需要保留旧角色兼容协议。本次迁移直接采用新的授权模型，旧岗位枚举不得继续作为服务端授权依据。

## 决策目标与非目标

### 目标

1. 将授权模型收敛为三级授权层级；
2. 明确平台与运营公司两个组织范围；
3. 以业务能力表达岗位职责；
4. 为运营任务、车主、车辆、行程建立统一状态—操作规划；
5. 保留默认拒绝、最小权限、职责分离和审计要求；
6. 为后续统一记录级 `allowedActions` 计算建立稳定契约。

### 非目标

1. 本批次不开放真实运营账号；
2. 本批次不启用生产能力；
3. 本批次不实现自定义角色编辑器；
4. 本批次不迁移安全、财务、隐私和数据导出的全部记录操作；
5. 本批次不允许客户端自行组合权限。

## 可选方案及权衡

### 方案一：保留现有岗位角色并增加别名

优点是改动较少，缺点是继续保留岗位与权限强耦合，并形成长期兼容层。项目尚未上线，没有保留该复杂度的必要。

### 方案二：三级层级直接决定全部权限

优点是表面简单，缺点是高层级会自动获得所有业务写权限，无法正确表达审计只读、技术恢复和财务职责分离。

### 方案三：三级层级、两个组织范围和业务能力组合

授权层级表达操作强度，组织范围表达数据边界，业务能力表达职责，记录状态和风险条件决定当前动作。该方案满足 MVP 减法，同时保留安全边界。

## 最终决策

采用方案三，并直接替换旧岗位授权模型。

### 三级授权层级

| 层级 | 名称 | 适用组织 | 最大授权边界 |
|---|---|---|---|
| `level_1` | 运营执行员 | 平台、运营公司 | 查看、认领、处理、补充材料和提交申请 |
| `level_2` | 运营负责人 | 平台、运营公司 | 分派、复核、关闭和组织内低风险限制 |
| `level_3` | 平台控制／独立审核 | 仅平台 | 跨组织治理、最终裁决和高风险独立复核 |

授权层级不自动继承全部业务能力。拥有 `level_3` 的审计人员仍然只能执行审计只读操作。

### 两个组织范围

平台工作身份必须携带明确的城市和运营公司范围，不得默认拥有全局通配范围。运营公司工作身份固定绑定一个运营公司，请求参数只能缩小范围。

### 业务能力

第一批统一能力包括：

- `operations_task`：运营任务处理；
- `operator_governance`：运营公司治理；
- `fleet_operation`：车主车辆运营；
- `fleet_review`：车主车辆审核；
- `trip_operation`：行程运营；
- `support_case`：客服案件；
- `safety_investigation`：安全调查；
- `safety_restoration_review`：安全恢复独立复核；
- `finance_operation`：财务操作制单；
- `finance_review`：财务独立复核；
- `privacy_governance`：隐私治理；
- `analytics_read`：聚合报表查看；
- `audit_read`：审计只读；
- `technical_recovery`：技术恢复；
- `executive_read`：经营聚合查看；
- `membership_governance`：组织成员治理。

### 旧岗位迁移

旧岗位不保留为公开授权字段。现有合成账号直接改写为层级、能力集合和展示岗位名称。完整迁移映射见 `spec/admin/role-access-matrix.yaml`。

### 记录允许操作

记录允许操作必须由服务端根据以下输入统一计算：

```text
授权层级
+ 组织范围
+ 城市范围
+ 业务能力
+ 记录归属
+ 记录状态
+ 风险分类
+ 职责分离条件
```

无匹配规则时默认拒绝。前端只消费服务端返回的允许操作和阻断原因，不得根据岗位名称推导权限。

## 产品和业务影响

1. 登录后仍显示岗位名称，但岗位名称只用于用户识别工作身份；
2. 后台导航由业务能力集合生成；
3. 成员页面展示授权层级和能力，不再展示可变的岗位角色标识；
4. 平台和运营公司后台继续使用同一产品外壳，但数据范围和能力不同；
5. 后续详情页将统一展示可执行操作、阻断原因和下一步。

## 安全、隐私、合规与公平性影响

1. 服务端是授权唯一事实源；
2. 客户端提交的层级和能力声明不可信；
3. 运营公司不得拥有 `level_3`；
4. 审计、技术和经营查看能力默认只读；
5. 制单人与复核人、安全调查人与恢复复核人必须不同；
6. 高风险操作继续要求原因、幂等键、版本校验和审计；
7. 字段脱敏、临时授权和导出审批不因本次层级简化而放宽。

## 验收标准

1. `AdminProductRole` 和 `productRole` 不再出现在公开后台契约和授权服务中；
2. 工作身份明确包含授权层级、能力集合和展示岗位名称；
3. 导航和操作权限仅由能力、层级、范围和状态计算；
4. 运营公司身份无法配置 `level_3`；
5. 所有现有合成账号完成直接迁移；
6. 越权、跨组织、跨城市、职责冲突和未知能力默认拒绝；
7. 合约测试、服务端测试、后台测试、类型检查和文档治理通过。

## 生效与退出条件

本决策在合成后台契约和服务端授权实现完成后生效。真实账号、真实组织成员或生产启用仍需重新完成身份、安全、隐私和生产批准。

若未来需要自定义岗位，只允许将岗位作为预定义能力模板，不得重新让岗位名称成为授权依据。
