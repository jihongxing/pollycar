# 决策 0008：App 前端技术选型

## 决策状态

`已批准`

批准日期：`2026-07-11`

决策人：产品负责人、工程负责人

## 背景与待解决问题

PollyCar 已确定用户端采用一个 App、一个账户，并通过显式身份上下文在乘客和车主之间切换。当前 `apps/app` 只有 TypeScript 沙箱配置，尚未具备移动端运行时、页面路由、服务端状态管理、表单、设计系统和自动化测试能力。

需要选择一套能够：

- 支持 iOS 与 Android；
- 保持 TypeScript 严格模式；
- 支持单 App 多身份导航；
- 以公开 API 契约连接 Server；
- 处理复杂审核表单、异步任务和关闭状态；
- 在内部沙箱使用合成数据；
- 后续接入原生安全、通知、位置和深链接能力；
- 不因快速原型而牺牲生产级边界。

## 决策目标与非目标

目标：

- 为首个车辆准入纵向切片提供可实施的移动端技术基线；
- 使 App 页面、状态、网络、表单、测试和设计令牌有清晰边界；
- 支持同一账户下乘客与车主身份安全切换；
- 保持真实登录、支付、邀请、位置、聊天和生产发布关闭。

非目标：

- 本决策不批准应用商店发布；
- 不批准真实用户或真实敏感数据接入；
- 不确定运营后台的最终前端框架；
- 不引入微前端、超级 App 容器或动态下发业务代码。

## 可选方案及权衡

### 方案 A：React Native 与 Expo

优点：

- 使用 React 与 TypeScript，和现有 workspace、契约及测试工具链一致；
- Expo 提供开发构建、原生能力封装和较完整的移动端工程体验；
- Expo Router 支持基于文件的路由、深链接和类型化路由；
- 可以在需要时加入原生模块，不把产品限制为纯 Web 容器；
- 适合先在内部沙箱快速形成端到端产品闭环。

缺点：

- 需要管理 Expo SDK 与 React Native 版本兼容；
- 高度定制的原生交互仍可能需要平台专项实现；
- 团队必须建立移动端性能、可访问性和发布治理能力。

### 方案 B：Flutter

优点：

- 跨平台一致性强；
- UI 渲染和动画控制完整；
- 适合高度定制的视觉系统。

缺点：

- 引入 Dart 和独立生态；
- 无法直接复用现有 TypeScript 契约类型和团队工具链；
- App 与 Server 的语言、测试和构建认知成本增加。

### 方案 C：原生 Swift 与 Kotlin

优点：

- 平台能力、性能和可访问性控制最完整；
- 对高复杂度原生功能具有长期上限。

缺点：

- 需要维护两套客户端实现；
- 当前阶段会显著增加人力、交付和规则一致性成本；
- 不适合先验证单 App 多身份和车辆审核闭环。

### 方案 D：响应式 Web 或 PWA

优点：

- 交付快；
- Web 调试和部署简单。

缺点：

- 后续位置、通知、后台任务、设备安全和商店分发能力受限；
- 容易把移动产品做成页面容器；
- 不符合长期原生 App 产品形态。

## 最终决策

采用 **React Native + Expo + TypeScript 严格模式**。

### 核心栈

- 移动运行时：React Native；
- 工程与原生能力：Expo；
- 路由：Expo Router；
- 服务端状态与请求缓存：TanStack Query；
- 本地界面状态：React Context 与局部 reducer；
- 表单：React Hook Form；
- 运行时契约校验：由 `packages/contracts` 提供 JSON Schema 派生或兼容校验器；首切片不得在 App 复制领域规则；
- 列表：优先使用 React Native 官方列表能力；出现实测性能问题后再决定专用虚拟列表；
- 动画：React Native Reanimated，仅用于身份切换、状态变化和必要反馈；
- 图标：统一线性图标集，经设计令牌封装，不允许页面直接混用多套图标；
- 测试：Vitest 保留纯 TypeScript 测试，React Native Testing Library 用于组件和页面交互，端到端框架在可运行首切片后单独批准。

### 状态边界

- Server 是业务状态唯一权威来源；
- TanStack Query 管理服务端状态、失效和重试；
- Context 只保存账户会话、当前身份上下文、主题和无敏感性的界面偏好；
- 表单草稿不得进入全局状态；
- 不引入 Redux、MobX 或其他全局状态框架，除非出现无法由上述边界解决的明确问题并另行决策。

### 目录边界

目标结构：

```text
apps/app/
  app/
    (shared)/
    (passenger)/
    (owner)/
  src/
    application/
    components/
    features/
    identity/
    infrastructure/
    screens/
    theme/
    testing/
```

- `app/` 只负责路由和布局组装；
- `src/features/` 按业务能力组织；
- `src/identity/` 负责当前身份上下文和安全切换编排；
- `src/infrastructure/` 负责 API 客户端、缓存、日志和适配器；
- `src/theme/` 是设计令牌和组件主题实现；
- 页面不得直接调用原生供应商 SDK或复制 Server 业务规则。

### 平台范围

- 产品目标平台：iOS 与 Android；
- 首个实现环境：Expo 内部开发构建；
- Web 仅可作为设计预览或辅助测试，不作为首期正式用户渠道；
- 应用商店、签名、推送、地图、真实身份和支付能力必须另行批准。

## 产品和业务影响

- 可以用同一代码库构建乘客和车主两个身份工作台；
- 身份切换、深链接、通知归属和页面状态可以在同一导航体系内实现；
- 首个车辆准入切片可从静态规格进入真实移动页面和交互测试；
- 团队无需在当前阶段维护两套原生客户端。

## 安全、隐私、合规与公平性影响

- 当前身份只用于界面上下文，服务端仍对每个命令重新鉴权；
- 本地缓存不得持久化身份原件、支付数据、精确位置、聊天证据或审核敏感原文；
- 日志、错误上报和开发工具必须执行敏感字段拒绝；
- 深链接必须验证目标身份和资源权限；
- App 不得根据用户性别、外貌、财富暗示或其他敏感画像改变可见性和排序。

## 验收标准

- App 可在严格 TypeScript 下完成构建和类型检查；
- 单一 App 能承载共享、乘客和车主路由组；
- 身份切换不能绕过目标身份准入或服务端授权；
- 网络状态、缓存、表单和页面状态职责清晰；
- 设计令牌由统一主题模块提供；
- 首个车辆准入页面具备组件测试和合成流程测试；
- 所有真实能力继续默认关闭。

## 生效与退出条件

立即作为 App 生产级代码实现的技术基线生效。

退出或替代条件：

- Expo 无法满足必要的安全、性能、可访问性或原生能力要求；
- 单一代码库导致平台体验或关键能力长期不可接受；
- 版本升级成本持续阻断交付；
- 出现需要原生专项客户端的已验证业务要求。

任何替代必须记录迁移成本、契约兼容和已实现页面处置方案。
