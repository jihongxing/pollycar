# 发起行程与预约时间设计

## 文档状态

- 状态：已实现，仅限内部生产级沙箱。
- 适用端：用户 App、车主工作模式、Server 行程服务。
- 当前能力边界：只允许内部沙箱和合成数据；真实支付、真实地图、真实设备位置和生产启用继续关闭。
- 关联功能：发起行程、预约行程、车主自主接单、行程取消、通知、异常恢复和时间冲突检查。

## 目标

在现有“上车点、目的地、乘车人数、可选乘车场景”基础上增加“希望上车时间”，同时支持：

- 默认尽快出发；
- 最近连续时间段的快捷预约；
- 从 Server 当前时间起未来 72 小时内的完整预约；
- 车主逐单自主决定是否接受即时行程或预约行程；
- 时间失效、断网、重复提交、未知结果和跨天恢复；
- 预约订单的冲突检查、提醒、取消和重新匹配。

产品不得把希望上车时间表述为准时到达保证，也不得通过预约能力改变车主自主接单原则。

## 核心产品决定

### 时间字段名称

统一使用：

```text
希望上车时间
```

不使用“保证上车时间”“司机到达时间”或其他构成确定承诺的表达。

### 即时与预约

行程时间分为两种模式：

| 模式 | 用户语义 | 系统行为 |
| --- | --- | --- |
| 尽快出发 | 用户确认后立即寻找可用车主 | 行程创建后立即进入车主可接订单池 |
| 预约时间 | 用户选择未来的希望上车时间段 | 创建预约订单，由符合条件的车主自主接受 |

默认模式为“尽快出发”。

### 未来三天的精确定义

预约上限采用滚动时间定义：

```text
最大预约时间 = Server 当前时间 + 72 小时
```

不采用“今天、明天、后天三个自然日”的定义。

页面可以同时出现今天以及未来三个日期，但最后一个日期只能展示仍位于滚动 72 小时范围内的时间段。

### 时间段长度

预约时间段固定为连续的 10 分钟：

```text
16:00–16:10
16:10–16:20
16:20–16:30
16:30–16:40
```

相邻可预约时间段不得无故出现空缺。因服务暂停或运营时段限制不可预约时，应明确显示不可用原因或直接隐藏对应时间段。

### 最小提前时间

第一阶段采用：

```text
最早预约时间 = Server 当前时间 + 30 分钟
```

计算结果向后取整到下一个完整的 10 分钟边界。

示例：

| Server 当前时间 | 最早预约时间段 |
| --- | --- |
| 14:20 | 14:50–15:00 |
| 14:21 | 15:00–15:10 |
| 14:25 | 15:00–15:10 |
| 14:31 | 15:10–15:20 |

距离当前不足 30 分钟的需求使用“尽快出发”，不创建预约订单。

## 发起行程页面

页面信息顺序：

1. 上车点；
2. 目的地；
3. 希望上车时间；
4. 乘车人数；
5. 乘车场景，可选；
6. 路线和费用摘要；
7. 主操作按钮。

### 默认状态

```text
希望上车时间
尽快出发 · 当前 14:25
```

主操作按钮：

```text
确认呼叫
```

当前时间只帮助用户理解即时语义，不构成固定上车窗口。

### 今天预约

```text
希望上车时间
今天 15:10–15:20
```

主操作按钮：

```text
预约今天 15:10
```

### 明天预约

```text
希望上车时间
明天 16:20–16:30
```

主操作按钮：

```text
预约明天 16:20
```

### 更远日期

```text
希望上车时间
7月15日 周三 16:20–16:30
```

主操作按钮：

```text
预约 7月15日 16:20
```

确认页和订单详情页必须同时展示完整日期、星期和时间段，不能只显示相对日期。

## 时间选择面板

用户点击“希望上车时间”后打开底部面板：

```text
选择希望上车时间

● 尽快出发
  当前 14:25

快捷预约

15:00–15:10    15:10–15:20
15:20–15:30    15:30–15:40

查看全部预约时间
```

默认选中“尽快出发”，快捷预约不自动选中。

## 快捷预约

### 生成规则

快捷预约展示：

```text
从最早可预约时间开始的四个连续有效时间段
```

示例：

```text
15:00–15:10
15:10–15:20
15:20–15:30
15:30–15:40
```

快捷预约不再使用“半小时后、一小时后、两小时后、四小时后”等固定偏移量。

### 有效时间段含义

快捷预约中的“有效”只表示：

- 位于未来 72 小时内；
- 满足最小提前时间；
- 位于 Server 返回的可预约服务时段；
- 未被平台暂停；
- 不属于系统维护窗口。

它不表示一定有车主接受，也不表示车辆一定在该十分钟内抵达。

### 跨天处理

当天剩余时间不足四个有效时间段时，快捷预约继续展示下一个有效日期的时间。

示例：

```text
今天 22:40–22:50
今天 22:50–23:00
明天 08:00–08:10
明天 08:10–08:20
```

运营时间不得硬编码在 App，由 Server 可用性接口返回。

### 自动刷新

- 用户未主动选择预约时间时，快捷预约随 Server 时间重新计算。
- 用户已经选择预约时间后，所选绝对时间段固定，不再随页面停留自动移动。
- 提交前由 Server 再次校验；时间失效时保留上车点、目的地、人数和场景，只要求重新选择时间。

## 完整预约时间

点击“查看全部预约时间”后进入完整时间选择器。

日期列表根据滚动 72 小时动态生成：

```text
今天 7月13日
明天 7月14日
后天 7月15日
周四 7月16日
```

每个日期下展示连续 10 分钟时间段。最后一个日期只能展示未超过 `Server 当前时间 + 72 小时` 的部分。

不可预约日期应显示：

```text
该日期暂无可预约时间
```

加载失败时显示：

```text
暂时无法获取预约时间

[重新加载]
```

App 不得在无法连接 Server 时自行生成并确认预约时间。

## Server 可用性模型

Server 是时间规则的唯一权威来源，建议提供：

```ts
type TripBookingAvailability = {
  serverNow: string;
  timezone: string;
  immediateAvailable: boolean;
  minimumLeadMinutes: 30;
  slotDurationMinutes: 10;
  latestScheduledAt: string;
  quickSlots: readonly PickupTimeSlot[];
  serviceWindows: readonly ServiceWindow[];
};

type PickupTimeSlot = {
  startsAt: string;
  endsAt: string;
  available: boolean;
};
```

`quickSlots` 默认返回最近四个连续有效时间段。

App 负责本地化显示，但不得改变时间段边界、可用状态和最大预约时间。

## 行程时间契约

```ts
type TripTimingMode = "immediate" | "scheduled";

type TripTimingSelectionSource =
  | "immediate"
  | "quick_slot"
  | "calendar_slot";

type TripTiming = {
  mode: TripTimingMode;
  requestedPickupStartsAt?: string;
  requestedPickupEndsAt?: string;
  timezone: string;
  selectionSource: TripTimingSelectionSource;
};
```

行程创建请求应包含：

```ts
type CreateTripRequest = {
  origin: PlaceReference;
  destination: PlaceReference;
  passengerCount: 1 | 2 | 3;
  scene?: TripScene;
  timing: TripTiming;
  idempotencyKey: string;
};
```

约束：

- 时间以 UTC 存储；
- 页面按 Server 返回时区显示；
- `createdAt` 表示订单创建时间；
- `requestedPickupStartsAt` 和 `requestedPickupEndsAt` 表示希望上车时间段；
- App 本地时间只用于展示，不作为最终校验依据；
- 相同幂等键不得创建多笔预约；
- 未知写入结果不得自动重复提交。

## 预约状态

预约行程建议使用：

```text
预约已创建
等待车主接单
车主已接受
等待准备
车主前往上车点
车主已到达
行程进行中
已完成
```

异常状态：

```text
预约已取消
预约未能匹配
车主无法履约
等待重新匹配
预约时间已失效
```

建议机器状态：

```ts
type ScheduledTripState =
  | "scheduled"
  | "matching"
  | "reserved"
  | "preparing"
  | "driver_arriving"
  | "driver_arrived"
  | "in_progress"
  | "completed"
  | "cancelled"
  | "unfulfilled";
```

## 车主自主接单

预约订单进入独立的预约订单列表，符合条件的车主逐单自主决定是否接受。

预约卡片优先展示：

```text
明天 16:20–16:30

人民广场
→ 上海虹桥站

预计行程 45 分钟
1 人 · 机场／车站

乘车人头像  性别图标

[暂不接单]  [接受预约]
```

平台不得：

- 强制车主接受预约；
- 因车主浏览订单而占用接单资格；
- 将未来预约错误显示为当前必须立即履约的订单；
- 隐藏时间冲突；
- 自动替车主接受修改后的预约。

## 时间冲突

车主接受预约前必须检查：

```text
前往上车点预计时间
+ 希望上车时间段
+ 预计行程时长
+ 行程结束缓冲时间
```

第一阶段采用 15 分钟行程结束缓冲。

时间明显重叠时禁用“接受预约”，并显示：

```text
该时间与已有行程冲突
```

预约只占用对应未来时间范围，不得把车主立即标记为当前履约中。

## 预约提醒

| 时间点 | 乘车人 | 车主 |
| --- | --- | --- |
| 创建成功 | 已创建预约，车主接受后通知 | 不适用 |
| 车主接受 | 展示车主和车辆资料 | 展示预约已确认 |
| 提前 24 小时 | 超过 24 小时的预约发送提醒 | 同步发送 |
| 提前 2 小时 | 提醒检查上车点、人数和时间 | 提醒确认可履约 |
| 提前 30 分钟 | 提醒准备前往上车点 | 提醒准备出发 |

预约临近但仍未找到车主时必须明确展示：

```text
该预约暂未找到车主
你可以继续等待、调整时间或取消预约
```

## 修改预约

### 车主尚未接受

乘车人可以修改：

- 日期和时间；
- 上车点；
- 目的地；
- 乘车人数；
- 乘车场景。

修改后重新校验时间、容量、路线和匹配条件。

### 车主已经接受

日期、时间、上车点、目的地和乘车人数属于实质修改，不允许直接覆盖原预约。

页面提示：

```text
车主已接受当前时间安排

修改时间或行程信息，需要取消当前预约并重新发起。
```

该限制保护车主基于原订单信息作出的自主接单决定。

## 预约取消

### 车主尚未接受

- 乘车人可以随时取消；
- 不消耗善意取消额度；
- 不产生资金责任。

### 车主接受后三分钟内

- 沿用现有三分钟无责任取消；
- 取消原因可选；
- 不消耗善意取消额度；
- 不产生资金责任。

### 接受超过三分钟且距离预约开始不少于两小时

- 允许取消；
- 个人计划变化可以使用善意取消额度；
- 安全、对方责任、平台责任和不可抗力不消耗额度；
- 真实支付关闭，只记录零金额责任。

### 距离预约开始不足两小时

- 必须选择取消原因；
- 进入现有责任判断；
- 可以使用剩余善意取消额度；
- 车主取消时重新开放预约匹配；
- 不保证一定可以重新找到车主。

## 错误与恢复

至少覆盖：

| 错误码 | 中文含义 |
| --- | --- |
| `TRIP_PICKUP_TIME_INVALID` | 预约时间无效 |
| `TRIP_PICKUP_TIME_IN_PAST` | 选择的上车时间已经过去 |
| `TRIP_PICKUP_TIME_TOO_SOON` | 预约时间距离现在太近，请选择尽快出发 |
| `TRIP_PICKUP_TIME_TOO_FAR` | 最多可预约未来 3 天 |
| `TRIP_PICKUP_TIME_UNAVAILABLE` | 该时间暂不可预约 |
| `TRIP_SCHEDULE_CONFLICT` | 该时间与车主已有行程冲突 |
| `TRIP_SCHEDULE_CHANGED` | 预约信息已更新，请确认最新时间 |
| `TRIP_SCHEDULE_RESULT_UNKNOWN` | 预约结果尚未确认，请勿重复提交 |

恢复要求：

- 页面刷新和 App 重启后恢复预约草稿；
- 前后台切换后重新读取 Server 时间和预约可用性；
- 日期变化后重新计算今天、明天和后天；
- 手机时钟与 Server 不一致时以 Server 为准；
- 时区变化时展示完整日期并要求重新确认；
- 创建请求超时后按幂等键读取最终结果；
- 已被车主接受的预约不得因刷新退回等待接单；
- 时间失效只清除时间选择，不清除起终点、人数和场景。

## 隐私与数据最小化

- 时间信息按行程数据管理，不单独形成长期行为画像。
- 不因预约时间推断用户职业、住所规律或敏感活动。
- 日志保留订单编号、时间窗口和结果，不记录不必要的页面操作轨迹。
- 场景仍为可选项，不得影响车主排序、价格、资格或安全自动决策。
- 预约时间和性别不得共同用于匹配、筛选、排序、推荐或差异化价格。

## 验收标准

### 正常路径

- 默认显示尽快出发；
- 快捷预约展示最近四个连续有效时间段；
- 可以选择今天、明天及滚动 72 小时内的日期；
- 车主可以自主接受或忽略预约；
- 预约接受后双方看到一致的完整日期和时间段；
- 到预约准备阶段后进入现有接驾和履约流程。

### 边界路径

- 最早预约时间按 Server 当前时间加 30 分钟并向后取整；
- 最大预约时间不超过 Server 当前时间加 72 小时；
- 快捷时间跨天时显示日期；
- 最后一天只显示 72 小时范围内的时间段；
- 相邻预约时间段连续；
- 车主容量和时间冲突均能阻止错误接单。

### 异常路径

- 时间过期、服务暂停、断网、超时和未知结果均有中文恢复入口；
- 重复点击不创建重复预约；
- 修改已接受预约不会静默改变车主承诺；
- 临近预约仍未匹配时不伪造车主或车辆状态；
- App 重启和前后台切换后状态正确恢复。

### 门禁

- 真实支付继续关闭；
- 真实地图和真实设备位置继续受独立门禁控制；
- 预约能力不得绕过成年资格、账户会话、车辆资格、容量、配额、安全限制或审计；
- 生产启用继续需要独立批准。

## 实施结果

- 已建立即时／预约时间公开契约、连续十分钟时段、最小提前三十分钟和滚动七十二小时 Server 权威规则。
- 已实现预约创建、零金额支付前置、等待接单、车主自主接受、未来保留、准备履约、未履约和取消恢复状态。
- 已实现未接单预约的日期、时间、上车点、目的地、乘车人数和场景修改；车主接受后禁止静默修改实质信息。
- 已实现车主未来预约冲突检查，计算前往上车点提前量、预计行程时长和结束缓冲。
- 已实现预约创建、接受、提前二十四小时、提前两小时、提前三十分钟和未匹配的合成提醒。
- 已实现车主取消未来预约后重新开放匹配、三分钟取消窗口、两小时边界、善意取消额度和零金额责任记录。
- 已完成 PostgreSQL 预约字段、索引和幂等键持久化，并使用 Podman PostgreSQL 验证迁移和数据库重启恢复。
- 已完成乘车人预约与完整修改、车主预约展示与自主接单的浏览器场景。
- 真实支付、真实地图、真实设备位置、真实通知和生产启用继续保持关闭。

## 实施顺序

1. 扩展行程时间公开契约和机器状态；
2. 建立 Server 预约可用性和连续时间段生成服务；
3. 扩展行程创建、持久化和幂等恢复；
4. 改造 App 发起行程页面和时间选择面板；
5. 建立预约订单列表、车主自主接单和时间冲突检查；
6. 建立预约提醒、修改、取消和重新匹配；
7. 补齐正常、边界、并发、离线和未知结果测试；
8. 更新 OpenAPI、操作策略、错误码、机器场景和路线图状态。
