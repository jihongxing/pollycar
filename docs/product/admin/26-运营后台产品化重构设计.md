# 运营后台产品化重构设计

## 一、设计背景

阶段一至阶段五已经证明多组织范围、服务端授权、追加式审计、组织与运力、行程客服安全、资金运营和高层驾驶舱等技术控制能够在内部沙箱中运行。

2026 年 7 月 15 日人工验收确认，当前控制台仍偏向内部能力验证台，尚未形成普通平台人员、运营公司人员和管理层可以持续使用的完整运营后台。

当前阶段状态为：

> 技术控制验收通过，但完整运营后台产品验收未通过。

本轮重构不扩大真实数据、真实资金或生产启用范围，目标是把现有能力重组为具备账号入口、组织身份、角色菜单、统一列表和产品化表达的运营后台。

## 二、重构目标

本轮重构完成后，运营后台必须满足：

1. 后台用户通过明确的邀请、激活和登录流程进入系统；
2. 平台用户与运营公司用户拥有不同且不可混淆的组织范围；
3. 功能角色决定菜单、页面、操作和字段权限；
4. 运营公司用户只能访问所属运营公司的数据；
5. 所有增长型列表具备统一服务端分页、搜索、筛选和排序；
6. 一级导航按业务域组织，不再平铺大量技术页面；
7. 普通页面使用业务语言，技术术语只出现在审计和诊断场景；
8. 每个角色均通过可见菜单、不可见菜单、数据范围和允许操作四类验收。

## 三、账号与组织身份

### 3.1 后台用户分类

所有后台用户至少分为两类：

- 平台内部用户；
- 运营公司内部用户。

平台内部用户的组织范围可以覆盖平台及授权的运营公司。运营公司内部用户的组织范围固定为所属运营公司，不得选择、查询或推断其他运营公司的数据。

一个自然人可以拥有多个组织成员关系，但单个登录会话必须固定一个当前工作身份，不得把多个组织的权限合并。

### 3.2 注册与开通方式

后台不提供面向公众的自由注册。账号开通固定采用：

```text
管理员发出邀请
→ 用户验证手机号或邮箱
→ 设置登录凭证
→ 完成多因素验证
→ 确认所属组织和功能角色
→ 激活账号
→ 登录后台
```

需要覆盖的入口状态：

- 登录；
- 接受邀请；
- 首次激活；
- 多因素验证；
- 忘记密码；
- 选择工作身份；
- 会话过期；
- 账号锁定；
- 账号停用；
- 无权限访问。

### 3.3 账号状态

后台账号状态固定包括：

- 待邀请；
- 待激活；
- 正常；
- 锁定；
- 暂停；
- 已离职；
- 已撤销。

平台账号只能由平台授权管理员管理。运营公司管理员只能管理本公司成员，不得创建平台账号、修改平台组织成员关系或授予平台角色。

## 四、权限模型

权限由组织身份与功能角色共同决定，两者不得互相替代。

统一授权公式为：

```text
允许访问
= 账号状态有效
+ 组织成员关系有效
+ 功能角色允许
+ 组织数据范围允许
+ 字段等级允许
+ 当前操作允许
```

平台用户不因属于平台而自动获得全部后台权限。平台身份只决定其最大组织观察范围，具体能查看和操作什么仍由功能角色决定。

### 4.1 平台角色

- 平台超级管理员；
- 平台运营；
- 运营公司管理；
- 平台客服；
- 平台安全；
- 平台财务经办；
- 平台财务负责人；
- 隐私合规；
- 审计；
- 高层管理。

### 4.2 运营公司角色

- 运营公司管理员；
- 运营负责人；
- 运力运营；
- 客服人员；
- 安全协作人员；
- 财务经办；
- 财务负责人；
- 公司管理层。

## 五、菜单和路由隔离

菜单不得继续由前端根据若干布尔门禁独立拼装。登录成功后由服务端返回当前工作身份对应的组织上下文、功能角色、权限集合和导航清单。

固定流程为：

```text
登录成功
→ 服务端返回当前组织和授权导航
→ 前端只展示授权菜单
→ 页面路由再次校验权限
→ 操作按钮和字段按权限展示
→ API 执行最终服务端授权
```

菜单分为：

- 公共菜单：工作台、通知、个人中心、帮助；
- 平台菜单：运营公司、跨公司运营、平台客服、安全治理、平台资金、全局审计、高层驾驶舱；
- 运营公司菜单：本公司工作台、本公司车主车辆、本公司行程、本公司案件、本公司资金、本公司报表。

运营公司用户不得看到平台菜单。未授权菜单不得采用“展示后点击报错”的方式处理。

菜单隔离之外必须同时覆盖：

- URL 直接访问；
- 页面路由；
- 操作按钮；
- 字段披露；
- 批量操作；
- 导出；
- 跨运营公司筛选；
- API 直接调用。

## 六、统一分页与列表能力

所有可能持续增长的数据列表必须使用服务端分页，包括：

- 运营公司；
- 后台账号；
- 车主；
- 车辆；
- 行程；
- 客服案件；
- 安全案件；
- 资金案件；
- 对账批次；
- 导出申请；
- 审计记录；
- 通知和任务。

统一列表请求与响应至少包含：

```text
page_size
cursor
next_cursor
has_more
total_count
filters
sort
query
```

默认每页 20 条，允许选择 20、50、100 条。搜索、筛选、排序和分页必须由服务端执行，不得由前端加载全部数据后自行分页。

统一列表体验包括：

- 关键词搜索；
- 状态筛选；
- 时间范围；
- 运营公司筛选；
- 排序；
- 上一页和下一页；
- 每页数量；
- 清空筛选；
- 空状态；
- 加载失败；
- 当前筛选条件导出。

运营公司用户的分页游标和筛选条件不得扩大其固定组织范围。

## 七、信息架构

全局一级导航重组为：

1. 工作台；
2. 组织与账号；
3. 运营公司；
4. 车主与车辆；
5. 行程运营；
6. 客服与安全；
7. 资金运营；
8. 数据与报表；
9. 高层驾驶舱；
10. 审计与系统。

一级导航控制在六至十个业务域。运营主体 360°、车主 360°、车辆 360°、主运营关系迁移和资金子页面应成为对应业务域的二级页面或详情页，不再全部平铺在全局导航。

不同角色登录后进入不同工作台：

- 平台运营进入平台运营工作台；
- 运营公司负责人进入本公司工作台；
- 客服人员进入待处理案件；
- 安全人员进入安全任务；
- 财务人员进入资金任务；
- 高层进入驾驶舱；
- 审计人员进入审计中心。

## 八、产品语言

普通运营页面必须移除或转换技术术语：

| 技术表达 | 产品表达 |
| --- | --- |
| 合成内部身份 | 体验账号或测试账号 |
| synthetic | 测试数据 |
| 功能门禁 | 功能暂未开放 |
| Server 授权范围 | 当前数据范围 |
| L2／L3 | 汇总数据／精确金额 |
| 幂等键 | 请求编号 |
| 资源版本冲突 | 数据已更新，请刷新后重试 |
| unclosed | 尚未完成日终关账 |
| 来源降级 | 部分数据暂未更新 |
| command recovery | 请求结果查询 |
| scope denied | 当前账号无权查看此数据 |

`Port`、`Adapter`、请求摘要、内部命令名和技术状态码不得出现在普通业务页面。

技术信息仅允许出现在：

- 审计详情；
- 系统诊断；
- 开发调试模式；
- 错误追踪信息。

业务页面必须说明：

- 当前发生了什么；
- 对业务有什么影响；
- 为什么暂时不能继续；
- 用户下一步可以做什么。

## 九、角色验收矩阵

每个角色必须验证：

1. 能看到哪些菜单；
2. 看不到哪些菜单；
3. 能查看哪些组织的数据；
4. 能执行哪些操作。

必须覆盖的负向场景：

- 运营公司用户修改 URL 访问其他公司；
- 客服人员访问资金页面；
- 财务人员访问安全证据；
- 高层用户执行业务审批；
- 运营公司管理员授予平台角色；
- 已停用账号继续使用旧会话；
- 菜单隐藏后直接调用 API；
- 翻页、搜索、排序或导出时扩大组织范围。

## 十、实施顺序

1. 冻结账号、组织成员关系和登录会话模型；
2. 冻结平台与运营公司角色权限矩阵；
3. 实现邀请、激活、登录、多因素验证和工作身份选择；
4. 将菜单改为服务端授权导航清单；
5. 实现统一路由守卫、无权限页面和操作级隔离；
6. 建立统一分页、搜索、筛选、排序组件及 API 契约；
7. 重组一级信息架构和角色工作台；
8. 全面清理技术文案并建立产品语言词典；
9. 按角色完成正向访问和越权访问验收；
10. 重新进行完整运营后台产品验收。

## 十一、实施门禁

在账号、登录、权限和会话契约批准前，不得进入新增认证代码实现。

在服务端导航清单和角色权限矩阵批准前，不得继续扩展现有硬编码菜单。

在统一分页契约批准前，不得为各业务页面分别实现不同分页方式。

在产品语言词典批准前，不得继续向普通页面增加技术状态名和内部命令名。

完整运营后台产品验收通过前，不得将阶段一至阶段五技术控制通过描述为“运营后台已完成”。
