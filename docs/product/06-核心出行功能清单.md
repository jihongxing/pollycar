## 产品模式

PollyCar 只有一个用户 App 和一个账户。

- 所有账户必须先完成成年资格验证，未通过验证不得使用任何业务功能。
- 成年资格验证必须通过身份证件核验、出生日期成年判定、本人活体检测和人脸一致性比对，并由验证结果取得姓名、证件号码和法定性别。
- 普通前端文案使用“成年资格验证”“确认已年满十八周岁”等表达，不使用“强制实名”“不实名不得使用”等强调强制性的表述。
- 身份证件和人脸信息可能由经批准的第三方身份服务处理；采集前必须完成必要告知和授权。
- 普通用户默认进入叫车首页，不显示“乘客身份”。
- 具备车主资格的用户可以主动进入车主工作模式。
- 车主工作模式明确显示“车主”、在线／离线和接单状态。
- 退出车主工作模式后返回默认叫车首页。

## 跨页面业务规则

### 自主接单

- 平台只展示符合资格、配额和容量的订单。
- 车主逐单决定接单或暂不接单。
- 不使用强制倒计时，不自动接受。

### 人数与容量

- 乘车人数必选，范围 1–3 人，默认 1 人。
- 车辆单次最大乘客人数范围 1–3 人，默认 1 人。
- 列表查询和接单命令均执行容量校验。

### 双方识别

- 头像用于识别。
- 性别来自已通过成年资格验证的身份证件结果，不提供隐藏开关。
- 性别在接单前向有权查看待接订单的合格车主弱展示，在接单后向当前行程乘车人弱展示车主性别；不向公开搜索、普通账户目录或无订单关系用户披露。
- 性别不得用于平台匹配、排序、资格、价格或风控自动决定。
- 车辆颜色、车型和车牌在车主接单后向乘车人披露。

### 取消

- 车主接单后 3 分钟内，乘车人有权主动取消。
- 取消原因和补充说明均非强制。
- 超过 3 分钟后的责任、收费和补偿规则需要后续单独设计。

### 到达确认

- 车主到达目的地使用滑动确认。
- 未滑动到底不得完成订单。
- 滑动失败、断网或未知结果时读取 Server 最新状态，不自动重复提交。

### 真实能力门禁

以下能力只允许设计和实现关闭态：

- 真实支付。
- 真实银行卡绑定。
- 真实结算和提现。
- 真实地图、定位和导航。
- 真实聊天内容。
- 真实订单、邀请和上海试点。

## 后续详细设计任务

### 第一组：导航与页面骨架

1. 定义默认叫车模式和车主工作模式的路由树。
2. 定义三个底部一级入口的身份差异。
3. 定义进入和退出车主工作模式的返回规则。
4. 定义所有页面的标题栏、底部操作区和安全入口。

### 第二组：地图与地点

1. 定义地图适配器和合成地图降级态。
2. 设计位置权限未授权、定位失败和无服务区域。
3. 设计地点搜索、最近地点和常用地点。
4. 设计地图加载、慢网和离线状态。

### 第三组：订单与履约

1. 设计行程创建、等待、接驾、上车、履约和完成状态转换。
2. 设计订单卡信息密度和车主自主接单交互。
3. 设计上车确认码。
4. 设计滑动到达控件的状态、手势和无障碍替代操作。
5. 设计超时、取消和未知结果恢复。

### 第四组：双方资料与公平性

1. 设计头像上传、默认头像和审核规则。
2. 设计实名法定性别的强制行程内披露、数据最小化和更正申诉。
3. 设计车主评分和乘车人评分模型。
4. 设计歧视、骚扰和滥用监测规则。

### 第五组：资金与订单

1. 设计车主订单列表和详情。
2. 设计资金中心信息架构。
3. 设计绑卡、提现、手续费、到账和失败状态。
4. 设计真实能力关闭态和沙箱合成结果。
5. 在支付、法律和税务批准前，不编写真实资金启用逻辑。

### 第六组：消息与安全

1. 设计行程临时会话生命周期。
2. 设计消息中心分类、未读和深链。
3. 设计举报、安全冻结和申诉入口。
4. 设计聊天、位置和安全证据的数据保留提示。

## 详细设计完成定义

每个功能进入代码前至少需要：

- 页面或组件设计稿。
- 正常、空、加载、失败、离线和无权限状态。
- 操作确认、重复点击和未知结果处理。
